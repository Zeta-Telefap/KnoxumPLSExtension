# High Walls: детальный разбор багов и исправление

## Что я подтвердил по PDF

Да, я вижу **две картинки на 12-й странице PDF**.

По ним видно следующее:
- у части новых стен освещение/шейдинг визуально ломается;
- в генерации реально проскакивают **плейсхолдерные материалы/текстуры** вместо нормального визуала комнаты;
- редактор и runtime ведут себя **не одинаково** по лампам.

---

## Корневые проблемы в текущем коде

### 1) Стены создаются через `PrimitiveType.Quad`
Это плохая база для production-кода в данном случае.

Почему это ломает картинку:
- `Quad` имеет один локальный нормаль-направление;
- ты полагаешься на поворот объекта и на то, как именно конкретный шейдер BB+/PLS трактует backface / double-sided / normal flip;
- в результате часть направлений выглядит случайно "нормально", а часть — нет;
- конкретно твой симптом **"юг/запад ок, север/восток не ок"** — типичный признак того, что геометрия строится не через свои нормали/winding, а через чужой примитив и надежду, что шейдер сам разрулит.

### 2) У новых стен и пола не переносится `MaterialPropertyBlock`
В `CreateWallQuad()` и `CreateBottomFloor()` у тебя делается только:

```csharp
pieceRenderer.sharedMaterial = mat;
```

Но этого недостаточно.

Почему:
- у плиток BB+/PLS визуал часто зависит не только от `sharedMaterial`, но и от **property block**;
- это особенно видно по коду `Cell.PrepareForPoster()` / `AddPoster()`, где используются `_PosterN`, `_PosterE`, `_PosterS`, `_PosterW`;
- если новый renderer не получил property block от исходной плитки, он может рендериться с дефолтными/плейсхолдерными значениями.

Итог:
- именно отсюда очень вероятно идут **не те текстуры / плейсхолдеры** на новых стенах;
- копировать надо **не только material, но и весь визуальный state renderer-а**.

### 3) Материал берётся небезопасно
Сейчас:

```csharp
MeshRenderer mainRenderer = tileComponent.GetComponent<MeshRenderer>()
    ?? tileComponent.GetComponentInChildren<MeshRenderer>();
```

Это опасно.

Почему:
- `GetComponentInChildren<MeshRenderer>()` может вернуть **не тот renderer**;
- после появления лампы это вообще может быть renderer лампы/декора, а не tile mesh renderer;
- в итоге пол/стены получают не материал плитки комнаты, а случайный дочерний renderer.

Правильно:
- брать **строго** `tile.MeshRenderer`;
- если его нет — уже потом осторожный fallback.

### 4) Пол ставится в неправильную высоту при `yOffset > 0`
Сейчас:

```csharp
floorObj.transform.localPosition = new Vector3(0f, -topY, 0f);
```

Где:

```csharp
topY = yOffset * 10 + (targetHeight - 1) * 10;
```

Это ошибка.

Почему:
- `tile.transform` уже перенесён на высоту `topY`;
- значит локальная позиция пола должна считаться **относительно верхней плитки**, а не от мирового нуля;
- правильное смещение нижнего пола:

```csharp
-(targetHeight - 1) * 10f
```

Текущая формула уводит пол вниз ещё и на `yOffset`, то есть ломает вертикальную геометрию у приподнятых комнат.

### 5) Лампы в редакторе остаются на старой высоте из-за порядка вызовов
Это ключевой баг по редактору.

Что происходит:
- ты вызываешь `ProcessCell3D()` в `Cell.LoadTile`/`Cell.SetShape`;
- внутри него вызывается `FixAndPositionLights()`;
- **но в редакторе `RefreshLights()` идёт позже**, и light prefab/LightController часто создаётся уже **после** твоей правки;
- значит твой код двигает лампы, которых в этот момент ещё нет;
- потом редактор создаёт лампы заново на дефолтной высоте 1 тайла.

Именно поэтому:
- **в игре нормально**,
- **в редакторе — нет**.

Правильная точка фикса:
- патчить `Cell.AssignLightController` и после назначения контроллера повторно выполнять light-fix.

### 6) Интенсивность света у тебя разгоняется при повторных вызовах
Сейчас:

```csharp
l.intensity = Mathf.Max(l.intensity, 3f) * Mathf.Sqrt(targetHeight);
```

Это очень опасно.

Почему:
- `ProcessCell3D()` может вызываться много раз;
- второй вызов уже берёт **увеличенную** intensity и умножает её ещё раз;
- третий — ещё раз;
- в итоге свет «разъезжается» по силе и становится непредсказуемым.

Это один из кандидатов на твой баг со **сломанным светом**.

Правильно:
- один раз сохранить **базовую intensity/range**;
- потом каждый раз считать новую intensity **от базы**, а не от уже модифицированного значения.

### 7) `DestroyImmediate()` используется и в runtime
Сейчас у тебя куча мест с `DestroyImmediate()`.

Это плохая идея для play mode.

Почему:
- `DestroyImmediate()` в runtime может давать неприятные побочки;
- для игры безопаснее обычный `Destroy()`;
- в редакторе вне play mode — `DestroyImmediate()`.

Правильно:
- сделать `SafeDestroy()`:
  - `Application.isPlaying ? Destroy(obj) : DestroyImmediate(obj)`.

### 8) Лишние коллайдеры и мусорные объекты
`GameObject.CreatePrimitive(PrimitiveType.Quad)` создаёт collider, который ты потом удаляешь.

Это:
- лишний мусор;
- лишняя работа;
- лишний шанс словить редакторные/runtime-артефакты.

Правильно:
- создавать пустой `GameObject`;
- вручную добавлять `MeshFilter` + `MeshRenderer`.

## Что я исправил в предлагаемом коде

Я подготовил файл:

- `HighWallsGenerator.fixed.cs`

В нём сделано следующее:

### По геометрии
- убран `PrimitiveType.Quad`;
- стены строятся **своим мешем** с явными нормалями;
- для каждого направления задаётся **внутренняя** нормаль комнаты;
- исчезает зависимость от случайного поведения backface/cull/double-sided.

### По материалам
- используется **tile.MeshRenderer** как источник;
- копируется:
  - `sharedMaterial`;
  - `MaterialPropertyBlock`;
  - `shadowCastingMode`;
  - `receiveShadows`;
  - probe settings.

### По полу
- нижний пол теперь ставится на корректную локальную высоту:

```csharp
-(targetHeight - 1) * 10f
```

а не на `-topY`.

### По свету
- введён `KnoxumLightBaseline` для хранения **базовой intensity/range**;
- `ApplyLightFixSettings()` больше не разгоняет свет при каждом повторном вызове;
- добавлен Harmony patch на:

```csharp
Cell.AssignLightController
```

чтобы лампы в редакторе фиксились **после фактического создания light controller**.

### По удалению объектов
- вместо безусловного `DestroyImmediate()` используется безопасный `SafeDestroy()`.

## Самые важные выводы в одну строку

Если максимально сжато, то у тебя сейчас было **четыре реальных корня** бага:

1. стены строятся на `PrimitiveType.Quad`, а не на своём меше с правильными нормалями;
2. на новые renderer-ы не переносится `MaterialPropertyBlock`;
3. в редакторе лампы правятся **до** их реального пересоздания;
4. интенсивность света считается от уже изменённого значения и разгоняется повторными вызовами.
