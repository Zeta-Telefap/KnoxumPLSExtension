# Build Mode / Builder Garage — дизайн-документ (черновик)

Статус: **дизайн обсуждается; BepInEx entry point `c` и прототип переноса `g` написаны, но не собраны и не проверены в игре**. Все числа и решения ниже помечены как «предлагается» и могут быть изменены.
Связанные документы: `CONTEXT.md`, `IDEAS.md`, `BUGS_AND_NEXT_STEPS.md`.
Подробный порядок написания механик: [`BUILD_MODE_IMPLEMENTATION_PLAN.md`](BUILD_MODE_IMPLEMENTATION_PLAN.md).

---

## 1. Идея в одном абзаце

Игрок может переставлять мебель (автоматы, шкафы, столы), двигать и сносить стены и двери
(синие стандартные / жёлтые распашные), а также пристраивать к школе новые комнаты
модулями 1x1 … 3x3. Товары Builder Garage — мебель, стены, двери и модули комнат —
покупаются за **YTP**. Ресток ассортимента оплачивается отдельно: игрок сдаёт в магазин
собранные объекты интерьера и стены.

## 2. Ключевые решения (черновые, «предлагается»)

| Вопрос | Черновое решение | Почему |
|---|---|---|
| Взаимодействие | **Всё в реальном времени, без паузы NPC** — правки не останавливают игру | Решение пользователя: стройка идёт «на ходу», Балди продолжает охоту |
| Перетаскивание | **G — поднять; ЛКМ — поставить; ПКМ во время переноски — бросить** в стиле Gravity Gun | Решение пользователя; переносимый объект удерживается перед камерой, бросок — физический |
| Покупка товаров | **YTP** за мебель, стены, двери и модули комнат | Все товары магазина имеют прямую цену в YTP |
| Ресток | Сдача собранных объектов интерьера и стен; за ресток также начисляются YTP | Сдача расходует собранное, а успешное обновление ассортимента даёт бонусные очки |
| Builder Garage | **Физическая комната** в свободном углу сетки + дверь из коридора | Сохраняет «зайти внутрь»; UI-вариант остаётся запасным |
| Граница уровня | Строим **только внутри существующей сетки** | `ec.cells` фиксированного размера; расширение наружу — отдельный проект |
| Собранное для рестока | Отдельный счётчик мода; ванильные 3 слота не трогаем | Снесённые объекты/стены сдаются магазину при обновлении ассортимента |
| Где живёт код | Отдельный класс/модуль + своя секция конфига, **не внутрь Chaos Mode** | Иначе второй файл на 3000 строк |

**Переноска через двери:** объект открывает незапертую дверь при касании её коллайдера или
меша, пользуясь штатным `Door.OpenTimed`. Если ширина стороны, захваченной при нажатии G,
превышает ширину одной клетки BB+ (10 мировых единиц), объект не открывает дверь; уже
открытая дверь закрывается заранее, если игрок ещё не у проёма. Запертые двери мод не отпирает.

## 3. Техническая база (по декомпилу `ultimate_dev_mods_decompile.cs`)

### 3.1 Клетки и стены

- **Стена — не объект.** Стена = биты покрытия граней клетки (`Cell.constBin`) + меш тайла
  `ec.TileMesh(constBin)` + коллайдеры `tile.Collider(dir)`. Отдельного GameObject стены нет.
- `ec.CloseCell(pos, dir)` — поставить грань (стену) с одной стороны.
- `ec.ConnectCells(pos, dir)` — убрать грань, открыть проход.
- `ec.UpdateCell(pos)` — пересчитать `constBin` по соседям (кто чья комната) → стены «сами»
  перерисовываются после смены принадлежности клетки.
- `ec.CreateCell / DestroyCell / SwapCell / MergeCell / RefreshCell` — низкоуровневые операции.
- `Cell.WallHardCovered(dir)`, `Cell.WallAnyCovered(dir)`, `Cell.HardCover/HardCoverWall/SoftCover` —
  проверка и установка покрытия.
- `Cell.SetShape()` внутри вызывает `ec.RecalculateNavigation()` + `GameCamera.RecalculateDijkstraMap()`
  → **дорого**, нужен батчинг (см. §5).

### 3.2 Комнаты

- `RoomAsset` (`ScriptableObject`): `cells: List<CellData>` (`pos` + `type`-бин), текстуры
  `florTex / wallTex / ceilTex`, `potentialDoorPositions / forcedDoorPositions`,
  `offLimits`, `eventSafeCells`, `standardLightCells`, `lights`, `spawnWeight`.
- `RoomAsset` собирается в рантайме: `ScriptableObject.CreateInstance<RoomAsset>()`.
- `LevelBuilder`:
  - `LoadRoom(asset, position, roomPivot, direction, lockTiles)` — построить комнату;
  - `LoadIntoExistingRoom(...)` — догрузить ассет в существующую комнату;
  - `ExpandArea(room, direction)` — расширить комнату на 1 клетку в сторону;
  - `DestroyRoom(room)` — снести комнату целиком;
  - `ManuallyBuildDoor(room, doorPre, pos, dir)` / `BuildDoorIfPossible(...)`;
  - `BuildWindowIfPossible(...)`;
  - `InstatiateEnvironmentObject(prefab, cell, dir)`.
- `RoomController.UpdatePosition()` пересчитывает bounds по клеткам; `room.cells`,
  `room.connectedRooms`, `room.roomsFromHall`.
- `RoomController.GenerateTextureAtlas()` → `ec.GetMatchingTextureAtlas(...)` **дедуплицирует**
  атласы по тройке текстур, так что наследование текстур хозяина не жрёт память.

### 3.3 Двери, стены-объекты, мебель

- `Door : TileBasedObject` — поля `ec`, `position`, `direction`, `bOffset`.
  `StandardDoor` (синяя), `SwingDoor` (жёлтая, две створки в wall slot).
- `ec.SetupDoor(door, cell, dir)` + `door.Initialize()` — поставить дверь в готовую клетку.
- `EnvironmentObject` — часть мебели/интерактивных объектов: `coverage` (`CellCoverage`) +
  `tileShapeMask` + коллайдеры. Живёт под `room.objectObject`; клеточное покрытие надо переносить
  вместе с объектом.
- Не вся мебель — `EnvironmentObject`: декомпил `DeskBuilderStandard` и `LockerBuilder`
  показывает столы/стулья и шкафчики, создаваемые как `MeshRenderer` под комнатой или
  `Cell.ObjectBase`. Механика `g` обрабатывает такие renderer-модели по имени объекта.
  `SodaMachine` — `EnvironmentObject`.
- `TileBasedObject` (не двери) двигаются строго по сетке: `position` + `direction` и не входят
  в первую версию переноски.

### 3.4 Экономика и UI

- `Pickup` (`IClickable<int>`): `price`, `OnItemPurchased / OnItemDenied / OnItemCollected`,
  `AssignItem(ItemObject)`, `showDescription`, `repeatable`; можно использовать как образец
  продажи товаров за YTP.
- Механизм `Pickup` с `item == NoneItem` забирает предмет из выбранного слота игрока —
  полезный образец для сдачи собранного объекта при рестоке.
- `ItemManager`: `defaultInventorySize` (3) + стикеры, `AddItem / RemoveItem / items[]`.
- `StoreRoomFunction` + `StoreScreen` — рабочий образец магазина с рестоком
  (`PurchaseRestock`, `Restock`, `ItemPurchased`, Johnny-аудио); интерфейс магазина можно
  переиспользовать, заменив оплату ассортимента на сдачу собранных объектов/стен.
- `WeightedSelection<T>` — пул ассортимента.

### 3.5 Карта, свет, навигация

- `Map`: `tiles: MapTile[,]`, `foundTiles: bool[,]` создаются при старте → новым клеткам нужны тайлы.
- `ec.GenerateLight / RegenerateLight / QueueLightControllerForUpdate / UpdateLightingAtCell`;
  `ec.lightMap[x, z].RegenerateLightSources()` вызывается в `SwapCell` автоматически.
- `ec.RecalculateNavigation()`, `ec.BuildNavMesh()`, `ec.QueueDijkstraMap(map)`.
- `ec.CullingManager.UpdateChunk(chunkId)` — чанки строятся под `levelSize`.

## 4. Ограничения и риски

1. **Фиксированная сетка.** `ec.cells = new Cell[levelSize.x, levelSize.z]` и массивы `Map`
   создаются один раз. Пристройки — только в свободные клетки внутри уровня.
2. **Navmesh / Dijkstra.** Любая правка формы клетки тянет пересчёт навигации → фризы.
   Нужна модель-черновик + один коммит.
3. **Свет.** Новые клетки без источников — чёрная дыра. Нужны `standardLightCells`/`GenerateLight`.
4. **Карта (M).** Без новых `MapTile` пристройки не видно на миникарте.
5. **`ec.rooms` = спавн.** События/предметы/NPC выбираются по комнатам → новой комнате нужны
   `offLimits = true` и `eventSafeCells`.
6. **Сущности в клетке.** Удаление клетки с NPC/игроком или двери, в которую идут, — риск NRE.
   Нужна проверка «здесь кто-то есть — операция запрещена».
7. **Сохранения.** Игра сохраняется между этажами; постройки исчезнут без своего оверлея
   (файл мода, ключ = seed + этаж).
8. **Атласы.** Каждая новая тройка текстур = отдельная текстура атласа (дедуп есть, но не бесплатен).
9. **Масштаб.** 1 клетка = 10×10 юнитов; обычный класс — несколько десятков клеток.
   1x1 — чулан. Ходовые размеры: 2x2, 2x3, 3x3, 3x4.
10. **Активити/ноутбуки.** Пристройка не должна создавать `Activity` — иначе ломается прогресс Балди.

## 5. Режим «на ходу» — что это меняет

Игра не ставится на паузу: NPC ходят, Балди охотится, двери открываются, пока игрок
переставляет стол. Это возможно, но меняет архитектуру: **никакой «черновой» геометрии**,
которая живёт в мире до коммита, и **никаких многокадровых правок без защиты**.

### 5.1 Три правила

1. **Превью — не геометрия.** Призрак стены/двери/мебели рисуется отдельным объектом
   с выключенными коллайдерами. Мир (`ec.cells`) меняется только в момент подтверждения.
2. **Одна правка = один атомарный коммит в одном кадре.** Внутри коммита:
   `ec.FreezeNavigationUpdates(true)` → все операции с клетками → `FreezeNavigationUpdates(false)`.
   `RecalculateNavigation()` при заморозке — no-op (проверено в декомпиле), поэтому
   батч из 10 операций даёт **одну** пересборку, а не 10.
3. **Сначала проверка, потом изменение.** `DryRun()` до применения: свободны ли клетки,
   нет ли NPC/игрока/предмета, не занята ли дверь, не отрежет ли это путь
   (`ec.CheckPath`/`NavigableDistance` до коммита).

### 5.2 Опасные места в реальном времени

| Операция | Риск | Защита |
|---|---|---|
| Удаление стены/клетки | NPC/игрок внутри → провал сквозь пол или NRE | Проверка `ec.Npcs`, `ec.Players` по клетке; запрет или «выталкивание» |
| Удаление двери | Дверь в процессе открытия/прохода NPC | `Door` занята → отказ, `bOffset`/створки проверять отдельно |
| Закрытие стены | Отрезает NPC от пути → он застревает | `CheckPath` из позиции каждого NPC в его цель; отказ, если путь рвётся |
| Снос мебели | В объекте стоит NPC / это укрытие | Проверка `Cell`-ссылок и `coverage` перед удалением |
| Пристройка комнаты | Десятки клеток + свет + карта + navmesh = фриз | Сборка по кадрам в корутине (см. §5.3) |

### 5.3 Пристройка комнаты по кадрам

Полная сборка комнаты — это `LoadRoom` + свет + `MapTile` + navmesh, и в один кадр это
даст заметный хитч. Предлагается «стройка» как процесс:

1. Игрок подтверждает пристройку → клетки помечаются `Cell.locked = true` и получают
   визуал «строительных лесов» (или полупрозрачный пол).
2. Корутина раз в N кадров применяет порцию (по 1–2 клетки), между порциями — `yield`.
3. По завершении: освещение, `MapTile`, один `BuildNavMesh()`, снятие `locked`.
4. **Стройка шумит:** `ec.MakeNoise(pos, value)` на каждую порцию → NPC идут на звук.
   Это и баланс, и фича: строишь — рискуешь.

Такой же паттерн уже используется в игре при генерации уровня (`TicksAtBeginningOfFrame`
+ `frameTickLimit`), то есть подход не противоречит движку.

### 5.4 UX без паузы

- Всё на горячих клавишах, без модальных окон: выделил → действие → подтвердил.
- Игрок может двигаться с объектом перед камерой: G поднимает его, ЛКМ ставит на ближайшую допустимую клетку под прицелом, ПКМ бросает физически.
- Отмена (undo) работает мгновенно и так же атомарно.
- Индикаторы в HUD: баланс YTP, собранные для рестока объекты/стены, «руки заняты», «здесь нельзя строить» с причиной.
- Ошибки объясняются одной строкой («NPC в клетке», «перекроет проход», «нет материала»),
  а не молчанием.

## 6. Архитектура (предлагается)

Разделение на **модель** и **применение**:

```
BuildModel (свои данные)   →  DryRun()  →  ApplyChanges()  →  EnvironmentController / LevelBuilder
- очередь правок                          (FreezeNavigationUpdates(true) → операции →
- undo-стек                                FreezeNavigationUpdates(false), один кадр)
- счётчик собранных объектов/стен для сдачи при рестоке
```

Никакого «режима» как отдельного состояния игры: инструмент всегда доступен, паузы нет.
`BuildModeController` — это скорее «активный инструмент + очередь правок», а не экран.

Целевое разделение файлов (entry point `c` и прототип переноса `g` уже созданы):

```
src/BuildMode/BuildModeController.cs   // вход, режим, коммит
src/BuildMode/BuildModel.cs            // черновик правок + undo
src/BuildMode/WallTool.cs              // грань: поставить/убрать/снести
src/BuildMode/DoorTool.cs              // синие/жёлтые двери
src/BuildMode/Plugin/c.cs              // BepInEx entry point
src/BuildMode/Tools/g.cs               // G захват, ЛКМ установка, ПКМ физический бросок
src/BuildMode/RoomBlueprint.cs         // RoomAsset из шаблона 1x1…3x3
src/BuildMode/RestockCollection.cs    // учёт собранных объектов и стен
src/BuildMode/BuilderGarage.cs         // магазин, покупки за YTP, сдача на ресток
src/BuildMode/BuildModeHUD.cs          // оверлей/призрак/подсказки
src/BuildMode/BuildModeInspector.cs    // dev-инспектор (этап 0)
```

Конфиг (BepInEx, отдельная секция `BuildMode`):
`Enabled`, `CountDemolishedForRestock`, `MaxRoomSize`, `GarageSpawnChance`,
`RestockCostItems` (1–3), `AllowGridGrowth` (false), `BuildNoise` (сила шума при стройке),
`RoomBuildFrames` (за сколько порций собирается пристройка), `ProtectPaths` (true — не рвать путь NPC).

## 7. Экономика и ресток (черновик правил)

**Покупки — за YTP.** Игрок тратит YTP на любые товары Builder Garage: мебель, панели
стен, двери и модули комнат. У каждого товара своя цена в YTP; цены и баланс будут
настраиваться после игрового тестирования.

**Ресток — за собранные объекты и стены, с наградой в YTP.** Чтобы обновить ассортимент,
игрок сдаёт магазину добытые при разборе объекты интерьера и стены. После успешного
рестока игрок дополнительно получает YTP; эти очки остаются валютой для покупок товаров.
Сдача не заменяет оплату YTP за покупку. Ванильные слоты инвентаря не используются как
постоянное хранилище: собранное учитывается отдельным счётчиком/пулом мода и расходуется
при рестоке.

| Что собрано | Учитывается для рестока |
|---|---|
| Снесённая стена | 1 единица стены/материала |
| Снесённый предмет интерьера | 1 единица объекта |
| Убрана дверь | 1 единица объекта (предварительно) |
| Разобрана пристройка | материалы учитываются по её составу (правило возврата уточнить) |

**Черновое правило:** один ресток требует сдать 1–3 собранные единицы — объекты,
стены или их сочетание. Конкретное количество и влияние ценности сданного на качество
нового ассортимента пока не зафиксированы.

**Цена временем и шумом.** Так как игра не встаёт на паузу, у каждой операции есть вторая
цена — внимание NPC: снос стены, перенос мебели и особенно сборка пристройки вызывают
`ec.MakeNoise(pos, value)`. Строить под носом у Балди дорого не только YTP и материалами,
но и нервами.

## 8. Этапы реализации

| Этап | Что | Зачем | Критерий готовности |
|---|---|---|---|
| 0 | **Dev-инспектор**: оверлей «клетка/стена/дверь/объект под прицелом» + поля + лог | Без него гадаем, почему меш/бин не тот | Видно `constBin`, `room`, покрытие, `TileBasedObject` |
| 1 | **Снос/восстановление стены и двери** | Проверяет `UpdateCell/ConnectCells`, свет, карту, navmesh | Снёс стену в игре → нет фриза, никто не застрял, карта цела |
| 2 | **Инструмент правки без паузы**: сетка, призрак, атомарный коммит, undo | База для всего остального | Правка применяется в одном кадре, NPC не застревают, отмена работает |
| 3 | **Перенос мебели** | Самая частая операция | Объект переносится, `coverage` обновлён, NPC обходит |
| 4 | **Строительство стен/дверей** | Проверяет установку геометрии; затем товар оплачивается в Builder Garage за YTP | Поставил стену/дверь, всё проходимо; бесплатный debug placement отключён в релизе |
| 5 | **Пристройки-комнаты** (`RoomAsset` из шаблонов) | Ядро идеи | Новая комната со светом, картой, дверью, без событий |
| 6 | **Builder Garage + покупки за YTP + ресток** | Экономика | Товары покупаются за YTP; сдача собранного обновляет ассортимент и начисляет бонусные YTP |

Порядок сознательно от дешёвого к дорогому: каждый этап играбелен и проверяем,
и любой этап можно «поправить», не переделывая предыдущие.

## 10. Захват предметов (`g`): как выбирается цель

**Принцип: подсвеченный предмет — это ровно тот предмет, который поднимет G.** Подсветка и клавиша
берут цель из одного запроса, который выполняется раз в кадр (`ResolveAimThisFrame`). Опроса по
таймеру, «липкости» и повторного поиска в момент нажатия больше нет.

**Правила выбора (по порядку):**

1. Луч идёт из камеры по центру экрана (`RaycastNonAlloc`, дальность 16, триггеры игнорируются),
   попадания сортируются по расстоянию. Игрок и предметы в полёте после броска не считаются ни целью,
   ни преградой.
2. **Первая твёрдая поверхность решает.** Если это коллайдер поднимаемого предмета — он и есть цель.
   Если это стена, дверь, окно, NPC или предмет, который нельзя носить, он закрывает всё, что за ним:
   сквозь геометрию ничего не поднимается.
3. **Помощь прицеливания.** Предмет, которого луч физически не коснулся (нет коллайдера или в
   коллайдере дыры, например открытая спинка стула), ищется по мешам: луч проверяется против
   локального бокса каждого меша (а не против раздутого `renderer.bounds`). Предмет без коллайдера
   соревнуется с физическим попаданием по расстоянию. Предмет с коллайдером подключается, только если
   луч не попал в другой поднимаемый предмет. Во всех случаях предмет должен быть ближе первой твёрдой
   поверхности. Реестр таких предметов строится порциями (~1 мс за кадр) и обновляется при смене уровня
   и раз в 20 секунд.

**Какой стороной предмет к игроку.** В руках к игроку обращена та сторона предмета, на которую смотрел прицел:
из четырёх горизонтальных осей предмета выбирается та, что лучше всего совпадает с нормалью поверхности под прицелом
(`Candidate.AimNormal`), а при подборе по коробке меша или при нормали вверх или вниз — сторона, обращённая к игроку.
Шкафчик или торговый автомат, на который смотрят спереди, несут лицом к себе. Пока предмет в руках, камера
поворачивает его плавно, сторона остаётся той же (`CarryState.SideYaw`). Подробности: §16.6.

**Что нельзя поднимать** (`ForbiddenPickupReason`): лифты, предметы-`Item`, облака (`CoverCloud`),
всё, внутри чего есть настоящий источник света (лампы, светильники), и имена с подстроками
`elevator`, `lift`, `lamp`, `light`, `chandelier`, `sconce`, `bsoda`, `no squee`, `covercloud`,
`chalkcloud`. Собственное свечение мода (объект `Carry placement glow`) в эту проверку не входит.

**Почему раньше «через жопу»:** подсветка добавляла предмету дочерний `Light`, а проверка «нельзя
поднимать» отвергала любой корень с дочерним `Light`. Подсвеченный предмет становился «запрещённым»:
подсветка мигала, G на подсвеченном предмете отказывала («Highlighted pickup is no longer
available»), а нажатие поглощалось. К этому добавлялись опрос подсветки раз в 0.25 с с запасом 0.35 с
и гистерезисом, три независимые точки входа для G и запасной поиск по раздутым AABB без учёта
преград.

## 11. Где остаётся брошенный предмет (`g`)

Код этого раздела **не собирался и не запускался в игре**: проверены только синтаксис (tree-sitter),
арность вызовов и то, что каждый используемый член существует в декомпиле BB+.

### 11.1 Правило

**Почему объект «появлялся не там».** `SettleThrown` определял комнату по **игроку**: если предмет
приземлялся в другой комнате, его переносили в ближайшую клетку комнаты бросающего («держим по свою
сторону стены»). Кроме того, `TryPlace` требовал, чтобы игрок мог дойти до клетки приземления.
Теперь **брошенный** предмет остаётся там, где остановился, даже в комнате, куда игрок не попадает;
проверяется только физическая свободность места. Брошенный через окно предмет разбивает окно и
остаётся в соседней комнате. Предмет, **выпущенный ЛКМ** (`DropHeld`), сохраняет прежнее правило
«комната игрока». Как предмет летит и почему не проходит сквозь стены: §12.

### 11.2 Проверка в игре

1. **Бросок в стену** (ПКМ): предмет отскакивает и падает у стены; в логе `Thrown prop hit …`.
2. **Бросок через окно:** окно разбивается, предмет остаётся в соседней комнате (`came to rest in`
   показывает другую комнату, чем `the player is in`).
3. **Бросок в дверь:** незапертая открывается и пропускает, запертая отбрасывает.

### 11.3 Лог

| Строка | Значение |
|---|---|
| `Prop '<имя>' thrown came to rest in <комната> (<категория>), cell (x, z); the player is in <комната>; wall impacts on the way: N.` | итог: где предмет остался |
| `No free spot for the prop near … it went back to where it came from.` | в комнате приземления нет свободного места: возврат на исходное |
| `A prop was still airborne after 8 s` | предмет не приземлился за 8 с |

### 11.4 Ограничения

- Всё в §11 проверено только статически (см. начало раздела).
- Ограничения полёта (стены, пол, потолок, `BoxCast` по мебели): см. §12.4. Для повёрнутых предметов
  по-прежнему используется AABB рендереров (запас консервативный).
- Брошенный предмет может остаться в закрытой комнате, куда игрок не дойдёт: так задумано.

## 12. Бросок без проходов сквозь стены и пол (`g`)

Код этого раздела **не собирался и не запускался в игре** (в песочнице нет .NET и DLL игры). Проверен только
статически (синтаксис, вызовы, существование членов игры по декомпилу BB+) и на Python-моделях логики; модели в
репозиторий не включены.

### 12.1 Бросок (ПКМ) и выпуск (ЛКМ): собственный полёт вместо физики Unity

**Что было не так раньше.** `BoxCast` поверх динамического `Rigidbody` не видел стену, если предмет уже
касался её на старте (бросок вплотную), проверял уменьшенную коробку и скорость до шага физики, пропускал пол
и потолок. У пола нет горизонтального коллайдера, а у края карты предмет улетал в пустоту до таймаута в 8 с.

**Что сделано.** Предмет стал кинематическим телом, и двигает его только `StepFlight` (каждый `FixedUpdate`);
физика Unity в полёте не участвует:

- старт: ПКМ — `PlayerVelocity·0,35 + направление·20`, ЛКМ — предмет просто падает; гравитация, сопротивление,
  скорость не выше 80;
- путь каждого шага проверяется по сетке клеток (`FlightGridSweep`): преграда — стена на ребре, пустота
  (`ConstBin == 16`), край карты, закрытая дверь; пол (y = 0) и потолок (y = 10) — плоскости (`FlightPlaneSweep`);
- удар — отскок (`FlightReflect`), удар о пол — посадка;
- старт у стены (`ResolveFlightStart`): центр предмета не может оказаться за стеной от камеры; если коробка
  предмета попала в стену, берётся ближайшее свободное место, иначе коробка временно уменьшается и потом
  растёт обратно;
- окно разбивается, незапертая дверь, в которую предмет проходит, открывается, запертая работает как стена;
  `BoxCast` оставлен только для мебели и прочих свободных коллайдеров;
- посадка: `SettleThrown` (как в §11.1) плюс проверка коробки полного размера по стенам и дверям (§16.5);
  таймаут 8 с остался как страховка.

Удалены `SweepAirborneProps`, `PassesThroughDoorOrWindow`, `ApplyWallBounce`, `TryGetGroundContact`,
`UpdateDoorForThrownProp` и константы `ThrowSweep*` / `ThrowBounce*`.

### 12.2 Проверка в игре

**Броски (ПКМ):** в стену вплотную, с 3 м, под углом, в угол, вдоль стены; вверх (потолок); вниз под ноги и
вперёд-вниз; к краю карты; в закрытое окно (разбивается), в незапертую дверь (открывается), в запертую (отскок);
большой предмет (шкаф, парта) почти вплотную к стене. Предмет не должен проходить сквозь стены и пол. Выпуск ЛКМ
вплотную к стене: предмет падает рядом.

### 12.3 Лог (`BepInEx/LogOutput.log`, префикс `[Rebuild the School]`)

| Строка | Значение |
|---|---|
| `Prop thrown; it flies on a swept path…` / `Prop dropped; …` | полёт начат (ПКМ / ЛКМ) |
| `Released next to a wall: …` | старт был вплотную к стене: предмет подтянут и/или коробка уменьшена |
| `Thrown prop hit <стена, закрытая дверь, потолок, коллайдер> at X u/s; bounced.` | первый удар за полёт (для выпуска `Dropped prop hit …`) |
| `Prop '<имя>' thrown came to rest in <комната>; …; wall impacts on the way: N.` | посадка |
| `Settling a landed prop failed…` / `Thrown-prop flight step failed…` / `A prop was still airborne after 8 s…` | ошибка или страховка: предмет вернулся на исходное место |

### 12.4 Ограничения и риски

- Ничего из §12 не запускалось в игре: первый запуск может показать ошибки.
- Высота потолка принята 10 (как в `HighWallsGenerator` и `Entity`), толщина стены ±0,1.
- Пока коробка предмета уменьшена (старт у стены), крупный предмет может визуально чуть заходить в стену;
  центр и коробка столкновений — нет.
- Полёт кинематический: предмет не толкает динамические тела; игрок и `Entity` не преграда для полёта
  (персонажей брошенный предмет толкает, см. §13).
- Невидимые твёрдые коллайдеры, не принадлежащие `Tile`/`Door`/`Entity`, видит только `BoxCast`.
- Реестр дверей обновляется раз в 0,25 с.

## 13. Брошенный предмет толкает персонажа со звуком Bang (`g`)

Код этого раздела **не собирался и не запускался в игре**; имена членов игры сверены только по декомпилу BB+.

### 13.1 Что делает

- Только бросок ПКМ; выпуск ЛКМ персонажей не трогает.
- Каждый шаг полёта (`StepFlight`) отрезок, который прошёл центр предмета (с запасом на размер его коробки),
  проверяется на пересечение с границами коллайдеров персонажей из `EnvironmentController.Npcs` (`HitNpcs`).
  Подходят активные, видимые, не замороженные и не раздавленные персонажи (замороженный `Entity` силы не
  применяет). Предмет должен лететь к персонажу, его горизонтальная скорость — не меньше 3.
- **Толчок как у хулигана.** `Bully.Push` делает `entity.AddForce(new Force(направление, pushSpeed, pushAcceleration))`
  со значениями 5 и −5 (сила гаснет за 1 с, сдвиг около 2,5). Здесь тот же вызов; направление — от точки удара
  через персонажа (по горизонтали), скорость = 0,5 · горизонтальная скорость предмета, но от 5 до 25, **умноженная
  на `NpcPushStrength` = 8** («пуш в 8 раз сильнее»), ускорение = −скорость. Сила длится 1 с и сдвигает на
  скорость / 2, поэтому множитель увеличивает и скорость, и расстояние. Бросок на 20 u/s: скорость 80, сдвиг около
  40 (4 клетки); верхний предел — 200 и 100 (10 клеток). Числа — константы `NpcPush*` в начале `g.cs`;
  `NpcPushStrength = 1` возвращает первую версию.
- **Звук.** `AudioManager.PlaySingle` на аудио-менеджере самого персонажа, так же 1st Prize играет `audBang`.
  Звук берётся по имени `Bang` (поиск описан в §14.1).
- Предмет отскакивает назад (горизонтальная скорость × −0,3). Каждого персонажа он толкает один раз за полёт.
  Стены, двери и пол по-прежнему решает полёт из §12: персонаж за стеной или закрытой дверью не задет.

### 13.2 Проверка в игре

1. Бросить предмет (ПКМ) в персонажа с 5–10 м: персонаж отлетает примерно на 4 клетки (40), слышен Bang, предмет
   отскакивает и падает.
2. Бросить в упор: то же самое.
3. Бросить мимо персонажа: ничего. Бросить в персонажа за закрытой дверью: удар о дверь, персонаж на месте.
4. Выпустить предмет ЛКМ над персонажем: толчка нет.

### 13.3 Лог

| Строка | Значение |
|---|---|
| `Thrown prop hit <имя> at X u/s; pushed it away at Y u/s (Bang); the player broke the Bullying rule.` | толчок выполнен, правило нарушено (§14) |
| `Sound 'Bang': found (<ассет>).` / `Sound 'Bang': not found, so it stays silent.` | результат поиска звука (§14.3) |
| `Pushing a character with a thrown prop failed…` | ошибка; полёт продолжается |

### 13.4 Ограничения и риски

- Имя ассета `Bang` и поле `audBang` взяты из декомпила, в игре не проверялись: нет звука — смотри вторую строку
  лога.
- Граница персонажа — прямоугольник вокруг его коллайдеров; у капсулы по углам он чуть шире.
- Персонаж с `resistAddend` на силы не реагирует (звук прозвучит); замороженный пропускается целиком.
- Персонажи вне `Npcs` не толкаются.
- При силе ×8 персонажа уносит на несколько клеток, возможно в другую комнату. Стены его останавливают:
  `Entity.MoveWithCollision` проверяет сферой весь путь кадра, а не только конечную точку.

## 14. Правило «Bullying», блок мыши и звуки полёта (`g`, `c`)

Код этого раздела **не собирался и не запускался в игре**; имена членов игры сверены только по декомпилу BB+.

### 14.1 Что делает

- **Правило.** Когда брошенный предмет касается персонажа (то же попадание, что в §13), игрок нарушает правило
  `Bullying`: `PlayerManager.RuleBreak("Bullying", 1, 0.25)`. Так же устроены питьё из фонтана и вход в учительскую
  (0,8 / 1 с и 0,25 с). Директор, увидев игрока в течение секунды после попадания (в сумме 0,25 с), гонится за ним
  и говорит `audNoBullying` (`Principal.Scold` знает `Bullying`). Числа — `BullyingLinger`, `BullyingSensitivity`.
- **Блок мыши.** Пока переносится предмет и `GameMouseBlockAfterRelease` = 0,3 с после броска или постановки,
  игра не видит мышь:
  - ЛКМ: `PlayerClick.Update` пропускается, клик не попадает в то, что видно в прицеле (раньше так было только во
    время переноса);
  - ПКМ: `ItemManager.UseItem` не выполняется, бросок не расходует выбранный предмет;
  - колесо: `ItemManager.IncreaseItemSelection` и `DecreaseItemSelection` не выполняются, инвентарь не листается
    (предмет вращается на R + колесо: это мод читает сам).

  Сам мод читает мышь через `UnityEngine.Input`, блок на него не действует. Патчи `ItemManager` ставит
  `g.TryPatchGameInput` из `c.Awake` после `PatchAll`: если метода нет, мод всё равно загружается.
- **Звуки** (`SoundObject` по имени; для `Bang` запасной вариант — `FirstPrize.audBang`, для `Ben_Gum_Whoosh` —
  `audWhoosh` у `Gum`; для `LockDoorStop` запасного нет). Все `SoundObject` индексируются один раз при первом
  обращении, при нехватке нужного звука индекс повторяется не чаще раза в 30 с.
  - Бросок ПКМ: пока предмет летит, зациклено играет `Ben_Gum_Whoosh`; звук идёт за предметом и обрывается при
    посадке (страховка — самоудаление через 10 с). Выпуск ЛКМ свиста не имеет.
  - Удар о стену, закрытую дверь, потолок или свободный коллайдер: `Bang` в точке удара, если скорость в препятствие
    не меньше 2,5, и не чаще раза в 0,2 с.
  - Касание пола или опоры (бросок и выпуск): `LockDoorStop` с громкостью 0,25 (`FloorSoundVolume`).
  - Источник — `AudioSourceManager`, обёртка самой игры: идёт через микшер эффектов, поэтому ползунок громкости
    игры действует. Звук объёмный, линейный спад между 10 и 70. Субтитров нет.

### 14.2 Проверка в игре

1. Выбрать предмет в инвентаре и взять предмет (G): колесо не листает инвентарь, R + колесо крутит предмет; ЛКМ
   ставит, ПКМ бросает и не расходует выбранный предмет; ещё 0,3 с после этого игра клики не принимает.
2. Бросить ПКМ: пока летит, слышен зацикленный `Ben_Gum_Whoosh`; удар о стену даёт `Bang`; касание пола даёт тихий
   `LockDoorStop`, свист обрывается.
3. Бросить предмет в персонажа на глазах у директора: он гонится и ругается. Если директор не видит, ничего.
4. Поставить предмет ЛКМ: тихий `LockDoorStop` при касании пола.

### 14.3 Лог

| Строка | Значение |
|---|---|
| `Sound '<имя>': found (<ассет>).` / `Sound '<имя>': not found, so it stays silent.` | один раз за исход: звук найден / не найден |
| `Thrown prop hit <имя> … the player broke the Bullying rule.` | попадание в персонажа (§13) и нарушение правила |
| `ItemManager.<метод> was not found…` / `… could not be blocked while a prop is carried…` | патч не поставился: игра продолжает читать этот ввод |
| `Playing the sound '<имя>' failed…` / `Starting the flight sound failed…` / `Indexing the sounds failed…` | ошибка звука; бросок не прерывается |

### 14.4 Ограничения и риски

- Имена `Ben_Gum_Whoosh` и `LockDoorStop` даны пользователем; `LockDoorStop` в коде игры не встречается (только в
  коде другого мода), так что если ассета нет, в логе будет `not found`.
- `ItemManager` блокируется на уровне действий, а не кнопок: пока переносится предмет, не работают и клавиши
  `ItemLeft` / `ItemRight`, и клавиатурная привязка `UseItem`, если они есть. Клавиши 1–9 не блокируются.
- Звук не распространяется по уровню, как у `PropagatedAudioManager`: слышен в радиусе 7 клеток сквозь стены.
- Правило нарушается при первом касании каждого персонажа за бросок; директор может не увидеть, тогда ничего не будет.
- Громкость и расстояния — константы в начале `g.cs` (`FloorSoundVolume`, `SoundMinDistance`, `SoundMaxDistance`).

## 16. Ванильные события и персонажи (`g`, файл `g.Events.cs`)

Код этого раздела **не собирался и не запускался в игре**; имена членов игры сверены только по декомпилу BB+.
`g` теперь `partial`: события лежат в новом файле `g.Events.cs` (его нужно добавить в проект, если проект
перечисляет файлы), а в `g.cs` — короткие вызовы `Fx…` внутри `try/catch`: ошибка события пишется в лог (не чаще
раза в 5 с) и обычный полёт не ломается.

### 16.1 Что делает

| Событие игры | Что происходит с предметом |
|---|---|
| **Бросок и пинок** | ПКМ бросает вдвое сильнее (`ThrowSpeed` 20 → 40, предел `FlightMaxSpeed` 80 тот же), толчок персонажа растёт вместе со скоростью. **Клик колёсика** без предмета в руках: предмет под прицелом (до `KickRange` = 14) бьют с того места, где он стоит: он не поворачивается и сохраняет коробку полного размера, летит как после ПКМ (`Whoosh`, `Bang`, толчок персонажа, «Bullying»), чуть от поверхности, на которой он лежит (иначе он сразу «приземлился» бы): вверх для предмета на полу, вниз для прилипшего к потолку; если взгляд направлен в эту поверхность (игрок на потолке смотрит на пол), удар идёт по горизонтали (§16.7); с предметом в руках колёсико бросает его, как ПКМ. Посадка и что исправлено в пинке: §16.5. |
| **Наводнение** (`Whirlpool`) | Водоворот ловит предмет магнитом. Предмет, коробка которого ближе радиуса шара + 4 ед. (`WhirlpoolMagnetExtra`), теряет свою боковую скорость (затухание 6/с, к центру сильнее) и идёт к центру со скоростью `(R − d) / R · 20` ед/с, умноженной на 1,5, но не меньше 5 ед/с (у края шара ванильная тяга равна нулю); стена по пути гасит тягу. Упав на пол в зоне, предмет скользит по полу дальше: полёт для него продолжается, `Whoosh` обрывается, тихий `LockDoorStop` играет один раз. В 5 ед. от центра, на полу, водоворот забирает предмет, как персонажа (`Whirlpool.Update`): он закрывается (слой 19, приватный `Close()`: уменьшается и исчезает), то есть **один предмет на водоворот**. Предмет за 0,4 с уходит в пол и за 0,4 с выходит из **другого водоворота наводнения** (случайного из оставшихся; тот остаётся открытым). Если других водоворотов не осталось, как в `Whirlpool.Teleport`, в случайной клетке формируется новый, он закрывается после выхода (§16.7). Если за 10 с предмет не дошёл до центра (на пути что-то стоит), магнит отпускает его, и он садится как обычно. Лежащие предметы не тянет. |
| **Гравитационный хаос** (`GravityFlipper`) | Предмет берёт гравитацию того, кто его держит. Игрок на потолке (`Entity.Flipped` при активном `GravityEvent`) держит предмет вверх ногами: при подборе предмет за 0,33 с переворачивается на 180° вокруг горизонтальной линии к игроку (`CarryState.CarryRoll`; прямая поза `CarryRotation` остаётся, сторона, на которую смотрел прицел, по-прежнему обращена к игроку). Выпущенный (ЛКМ) или брошенный (ПКМ) таким игроком, предмет падает вверх и прилипает к потолку (тихий `LockDoorStop`), пока гравитация не сменится (§16.7). Наоборот: игрок на полу берёт предмет с потолка, в руках предмет разворачивается обратно и после выпуска падает на пол. Пинок (клик колёсика) оставляет предмету его гравитацию и позу: предмет на потолке не разворачивается и летит вдоль взгляда. Коснувшись фигуры, предмет (как игрок и персонажи) «тратит» её (`DestroyFlipper`) и меняет гравитацию плавно: коэффициент 1,6/с, поворот на 180° за 0,5 с. После конца события гравитация возвращается. Предметы высотой с комнату не переворачиваются. Предмет на потолке твёрдый (игрок упирается в него, как в предмет на полу) и берётся как обычный: G или клик колёсика. |
| **Balder Dash** (`Balder_Entity`) | Предмет в объёме валуна сплющивается на 10 с, валун играет свой звук, как для персонажа. |
| **Молоток Доктора Рефлекса** (`DrReflex`) | Только пока он в `DrReflex_Hunting`: сфера радиуса 4 в 5 ед. перед ним сплющивает предмет на `squishTime` (30 с; читается рефлексией) и бьёт молотком (`Hammer(null)`). |
| **Супер-двери** (`LockdownDoor`) | Когда плита закрывающейся двери (она опускается) касается предмета, предмет сплющивается на 10 с, и дверь тут же идёт вверх (`Open`). Работает и вне ивента. Закрытая дверь для полёта — стена; открытая — проход. |
| **Student Shuffle** (`StudentCrowd_Follower`) | Летящий предмет, подошедший к студенту толпы ближе 3,5 ед. ниже его головы, поднимается на голову (скорость 20 ед/с) и едет вместе со студентом куда тот идёт. Когда студента нет (конец ивента), предмет падает со скоростью студента. Пока едет, его можно взять (G) или пнуть; таймаут возврата не считается. Единственное ограничение: в комнату event spawner предмет не заходит, у её границы он остаётся на месте и падает (§16.7); в остальных местах предмет едет на голове, как и раньше. |
| **Предмет на пути персонажа** | Персонажи **не пинают и не толкают** предметы, а обходят их. Ванильный `Navigator` двигает персонажа сдвигом `transform.position` к следующей точке пути и о предметах не знает. Каждый кадр мод смотрит на отрезок «персонаж → следующая точка пути». Если он подходит к предмету (границы рендереров на плоскости пола) ближе, чем радиус персонажа (0,8–1,5) + 0,15 − 0,3, перед отрезком вставляются 1–2 угла прямоугольника препятствия на расстоянии радиус + 0,2 (`Navigator.destinationPoints`, рефлексия). Предметы, между которыми не пройти (их зоны пересекаются), считаются одним препятствием. Выбирается самый короткий объезд, у которого каждая точка и каждый отрезок свободны от стен (`FlightGridSweep`, `FlightOverlaps`) и от других предметов; если такого нет, берётся объезд, у которого последний отрезок свободен только от стен и самого препятствия (следующий предмет персонаж объедет, когда дойдёт до него). Вставленные точки не пересматриваются, пока персонаж не дошёл до первой. Если он возвращается к уже достигнутому углу (кружит) или слишком часто меняет план, 10 с он идёт прямо. Следующая точка внутри препятствия пропускается (если до следующей можно дойти прямо) или сдвигается к краю; конечная цель не меняется. Предметы в руках и в воздухе не препятствие. |

Сплющивание — вертикальный масштаб 0,5, в последние 3 с колебание `sin((3 − t)·16π)·0,2 + 0,5`, как у
`Entity.Squish`; делает его компонент `PropFx` на предмете, он возвращает исходный масштаб и удаляется сам.
Предмет, который побывал в событии (потолок, водоворот, студент, фигура), оседает там, где приземлился, как
брошенный (правило комнаты для ЛКМ-выпуска к нему не применяется).

### 16.2 Проверка в игре

1. Клик колёсика по предмету в 5–10 ед., в том числе вплотную к стене и по предмету, стоящему боком: он летит в
   сторону взгляда, не поворачиваясь, `Whoosh` и `Bang`, как после ПКМ; после посадки он не в стене и не в
   дверном проёме, стоит там, где упал, и его можно снова взять (G) и поставить; ПКМ бросает заметно дальше, чем раньше.
2. Наводнение: бросить предмет в воду у водоворота — его сносит к центру, он уходит в пол и выходит из другого
   водоворота; тот, в который он вошёл, закрывается (проверка полная: §16.7).
3. Гравитационный хаос: бросить предмет в фигуру — гравитация предмета плавно меняется (проверка с потолком: §16.7).
4. Валун, молоток, супер-дверь: бросить предмет под них — он сплющивается; дверь поднимается.
5. Толпа студентов: бросить предмет в толпу — он едет по головам.
6. Поставить предмет (стол, шкаф, растение) посреди коридора на пути погони: персонаж обходит его, не проходя
   сквозь и не пиная. Два предмета рядом он обходит как один. Перегородить коридор предметами целиком: персонаж идёт
   прямо, как в оригинале.
7. Наводнение: бросить предмет мимо водоворота, в 2–4 ед. от края шара, и в сам шар: предмет притягивает, он не
   застывает на полу, звук полёта обрывается, предмет тонет и выходит из другого водоворота.
8. Гравитационный хаос: предмет на потолке не прозрачный: в него упираешься, его можно взять (G), он при этом
   разворачивается, его можно поставить, бросить и пнуть.
9. Пнуть питьевой фонтанчик несколько раз (клик колёсика), в том числе у границы коридора и комнаты: модель не
   пропадает, не остаётся один спрайт крана.
10. Взять шкафчик или торговый автомат спереди (G): в руках он повёрнут лицом к игроку. Взять его сбоку или сзади:
   к игроку обращена та сторона, на которую смотрел прицел.

### 16.4 Ограничения и риски

- Толкование: «водоворот внутри объекта» — тянет, пока шар водоворота пересекает коробку предмета; «супер-двери» —
  `LockdownDoor` (ивент Lockdown; что это «Процедура тестирования», по коду не проверено); «не игнорировать
  объекты» — персонаж обходит мешающий предмет (пинок персонажем убран по решению пользователя). Вариант
  «предметы твёрдые для персонажей» отброшен: слои коллайдеров предметов неизвестны.
- Радиус водоворота берётся из приватного `sphereCollider` рефлексией; вертикальное смещение тяги оригинала не
  учитывается.
- Сплющивание и перевёрнутый предмет — визуальные: коллайдеры растут и сжимаются с масштабом, но полёт считает
  коробку полного размера.
- Предмет на потолке и на голове студента берётся (G, пинок), но твёрдый только предмет на потолке; высоту головы
  мод измеряет по спрайту студента, при неудаче берёт 3,5. Предмет, закрепившийся на потолке прямо на игроке, может
  его вытолкнуть (игрок — `CharacterController`).
- Пока предмет не приземлился, сплющивание и тяга считаются по его текущей коробке; лежащие предметы валун, молоток
  и дверь сплющивают, а водоворот, потолок и студенты — нет.
- Магнит водоворота и скольжение по полу проверены только Python-моделью без стен и мебели: предмет, брошенный
  так, что его путь заходит в зону (радиус + 4 ед.), тонет в 97–98 % случаев, не дольше чем за 5 с (остальные —
  вскользь по самому краю зоны). Если по пути к центру стоит стол или другой предмет, магнит через 10 с отпускает
  предмет. В игре не проверялось.
- Сторона предмета при подборе: из четырёх горизонтальных осей предмета (+Z, +X, −Z, −X) выбирается та, что
  лучше всего совпадает с нормалью поверхности под прицелом (коллайдер); если прицел попал в предмет, у которого
  нет коллайдера (подбор по коробке меша), берётся сторона, обращённая к игроку. Предмет с лицом по диагонали
  выбирает сторону приблизительно.
- Объезд знает только предметы из реестра `g` (он заполняется по ходу прицеливания, пока предмет не в руках,
  поэтому в первые секунды уровня часть предметов не учтена) и их прямоугольник по X/Z (границы рендереров).
- Объезд не строит путь заново, а вставляет 1–2 точки у ближайшего мешающего препятствия; когда ванильная
  навигация перестраивает путь (смена целевой клетки, толчок), точки вставляются снова. Если обойти нельзя (проход
  перекрыт целиком, щель, в которую персонаж не помещается, скопление предметов, стены с двух сторон), персонаж идёт
  прямо сквозь предмет, как в оригинале. Обход идёт по углам прямоугольника, поэтому предмет сложной формы
  обходится с запасом.
- Логика объезда проверена только Python-моделью (коридоры и комнаты с 1–20 случайными предметами, перестроение пути
  в случайные моменты): персонаж, у которого есть путь, обходит предметы почти всегда, путь длиннее прямого в среднем
  на 1–12 %, зацикливание не наблюдалось. В игре не проверялось.
- Объезд работает для персонажей с `Navigator`, не замороженных и без `InteractionDisabled`.
- Из-за `partial` все части `g` должны быть `partial`, иначе проект не соберётся (CS0260).
- Числа — константы в начале `g.Events.cs`; `ThrowSpeed` — в начале `g.cs`.

### 16.5 Пинок и посадка: что было не так и что исправлено

Найдено чтением кода (в игре не проверялось). Пинок и бросок из руки идут по одному пути (`BeginCarry` →
`BeginFlight` → посадка `SettleThrown`), поэтому общие причины чинились общим кодом.

**Причины.**

1. Пинок сначала поворачивал предмет к камере (`BeginCarry`) и в том же кадре начинал полёт. `Transform` попадает
   в физику и в `Renderer.bounds` только после шага физики, поэтому границы были старыми: коробка полёта
   (центр, размеры) не совпадала с видимым предметом, и он заходил в стену или садился не там. При ПКМ предмет
   несут несколько кадров, поэтому там границы успевают обновиться.
2. Старт вплотную к стене (`ResolveFlightStart`) уменьшал коробку, и предмет мог сесть с уменьшенной коробкой.
   Проверка посадки `PropPlacementCollisionFree` (физика Unity) пропускает пары слоёв, которые матрица слоёв
   игнорирует, и стены не видит: предмет оставался в стене.
3. Предмет, севший в открытом дверном проёме, зажимался закрывающейся дверью (открытая дверь для полёта не твёрдая).
4. `ReleaseHeld` молча выходил, если у переносимого предмета уже не было `Rigidbody` или корня. `_held` оставался
   навсегда: нельзя ни бросить, ни взять другой предмет, мышь игры заблокирована. Это и есть «перестаёт
   работать перетаскивание».

**Исправления.**

1. `BeginCarry(..., keepRotation)`: пинок не поворачивает предмет. `BeginFlight(..., atRest)`: пинок стартует с места
   предмета с коробкой полного размера (проверка шага не затягивает коробку, уже касающуюся стены, глубже в стену).
2. `TryPlace` перед проверкой Unity проверяет аналитически (`FlightBoxClear`) коробку полного размера: она не
   должна пересекать стену, пустоту и ребро двери или окна (открытое и закрытое). Для повёрнутого предмета берётся
   квадрат, покрывающий любой угол. Если не подходит, работает кольцевой поиск ближайшего места
   (`TryPlaceNearby`), иначе предмет возвращается на исходное место. Это действует для любых посадок: бросок, пинок,
   выпуск ЛКМ.
3. `Update` и `ReleaseHeld` снимают застрявший `_held` (нет `Body` или корня): предмет возвращается на место, перенос
   снова работает.

**Ограничения.** Проверка по стенам аналитическая (сетка клеток, толщина стены ±0,1), по мебели остаётся проверка
Unity. Предмет, стоявший вплотную к двери или внутри стены, после выпуска ЛКМ садится на 0,1–0,3 ед. в стороне.
Пинок предмета, стоящего вплотную к другому предмету, не видит этот соседний предмет (начальные пересечения
`BoxCast` пропускаются); посадка потом сдвинет предмет, если места нет.

### 16.6 Второй отчёт: водоворот, потолок, фонтанчик, сторона подбора

Найдено чтением кода (в игре не проверялось).

**Причины.**

1. **Предмет застывает у водоворота, звук идёт.** Ветка «в водовороте предмет на полу не садится» (`StepFlight`)
   сдвигала предмет на долю шага до пола и кончала шаг. Предмет, который уже на полу, касается пола в начале шага:
   доля равна нулю, предмет не двигался, оставался «в полёте» до 120 с, `Whoosh` играл по кругу, а исчезал предмет,
   только когда игрок сам лез в водоворот. К тому же тяга начиналась только внутри шара и у края равна нулю:
   предмет, брошенный рядом, улетал со своей скоростью, а тот, что упал в шаре у края, замирал.
2. **Предмет с другой гравитацией «прозрачный».** Закрепившийся на потолке предмет оставался в списке летящих:
   прицел и подбор его пропускали, а коллайдеры игрока игнорировались до посадки. Сквозь него проходили, и взять
   его было нельзя.
3. **Пропадает модель фонтанчика.** Игра включает и выключает рендереры клеток `cell.renderers` вместе с чанком
   (`Chunk.Render`), и только когда чанк меняет видимость. Один рендерер может быть записан в списке дважды
   (построитель уровня и `CullingManager.PrepareOcclusionCalculations`) или в списке соседней клетки. Мод при подборе
   убирал первую запись в клетке-источнике. Оставшаяся запись прятала модель вместе со старым чанком там, где
   предмета уже нет; спрайт крана в списках не числится и оставался виден.
4. **Шкафчик и автомат берутся задом.** Подбор разворачивал предмет к игроку локальной осью +Z (по четырём сторонам
   света), а у шкафчиков и автоматов +Z — задняя сторона (у стены), лицо на −Z.

**Исправления.**

1. `StepFlight`: пока предмет на полу в водовороте, кончается только вертикальная скорость
   (`v.y = 0`, `FxFloorContact` — звук один раз), остаток шага идёт дальше (`continue`). Магнит `FxDrift`: зона
   радиус + 4 ед., скорость не меньше 5 ед/с и в 1,5 раза выше ванильной, своя боковая скорость предмета
   затухает; через 10 с без результата магнит отпускает предмет. `WhirlpoolSlideFriction` удалён.
2. `FxNotePinned` делает предмет на потолке твёрдым (`FxSetSolid`: коллайдеры игрока перестают игнорироваться,
   негладкие меш-коллайдеры включаются). Закрепившийся на потолке или едущий на студенте предмет (`FxResumable`)
   прицел и подбор видят, как обычный. `BeginCarry` сначала спрашивает `TryResumeCarry`: предмет выходит из списка
   летящих и несётся дальше со своим состоянием (откуда взят, покрытие, рендереры), при пинке он разворачивается
   в позу выпуска. Предмет, чья гравитация направлена вверх, студент на голову не ловит (`FxStepRide`).
3. При подборе рендереры предмета убираются из списков всех клеток (`RemoveRendererReferencesEverywhere`, все записи
   и разрушенные рендереры), а при посадке записываются в клетку и сразу получают видимость её чанка
   (`AddRendererReferences`).
4. `AimedSideRotation`: из четырёх горизонтальных осей предмета выбирается та, что лучше всего совпадает с нормалью
   поверхности под прицелом (`Candidate.AimNormal`); эта сторона разворачивается к игроку (`CarryState.SideYaw`
   сохраняет её, пока предмет в руках). Поворот по четырём сторонам света (`CameraCardinalRotation`) убран.
5. `FxResetScale` отменял «рост из 20 %». Сжатие предмета при входе в водоворот убрано в §16.7 (его заменил `FxAbortSink`).

### 16.7 Третий отчёт: загрузка этажа, спинка шкафчика, комната-спаунер, гравитация, наводнение

Найдено чтением кода. **Не собиралось, не запускалось в игре и не мерилось профайлером.**

**1. Загрузка этажа с множеством объектов (этаж 3).**

Причина (по коду, замера нет). `RefreshPlayer` каждый кадр, пока у игрока нет `ec`, вызывал
`FindObjectOfType<PlayerClick>()` — поиск по всей сцене. `ec` ставится только в конце генерации
(`BaseGameManager.Initialize` → `AssignPlayers`), то есть поиск шёл каждый кадр всей загрузки, и чем больше
объектов на этаже, тем он дороже. Похожие поиски по сцене были в событиях и в проверках дверей и окон.

Что сделано:

1. Игрок берётся из `CoreGameManager.GetPlayer(0)`. Пока уровня нет (`ec == null`), `Update` сразу выходит: за время
   генерации мод ничего не делает. Поиск по сцене остался запасным (раз в `PlayerSearchInterval` = 2 с, если
   `CoreGameManager` нет).
2. Двери: один `FindObjectsOfType<Door>()` на этаж (обновляется, если список старше `LevelDoorsInterval` = 120 с и
   он нужен). Границы окон считаются по мешам (границы выключенных рендереров ненадёжны).
3. Реестр предметов для прицела строится обходом контейнеров (`objectObject` комнат, `room.transform`,
   `cell.ObjectBase` только если он есть: геттер сам создаёт его), не больше `ProxyScanBudgetMilliseconds` = 1 мс за
   кадр, пересобирается раз в 60 с. Позиции и границы кэшируются (`ProxyBox`), по 64 предмета в кадр обновляется
   позиция.
4. События ничего не ищут по сцене: список событий этажа (§16.9; только `ec.GetEvent(...)` не годился, он знает лишь
   события таймера), публичный `FloodEvent.whirlpools`, приватный
   `GravityEvent.flippers` (рефлексия), дети `StudentEvent`, `ec.Npcs`, список дверей уровня. Сплющивание берёт
   предметы только возле своей зоны, обход персонажей — по кэшу позиций и меш-границ.
5. `IsSupportedPropName` запоминает результат по имени.

**2. Спинка красного и синего шкафчика.** `LockerBuilder` ставит `lockerPre` и `hideLockerPre`; задней стенки у них
нет (у стены её не видно). При подборе шкафчика (`EnsureLockerBack`) один раз создаётся дочерний объект `BackFace`: копия
всех мешей шкафчика (тот же `sharedMesh` и `sharedMaterials`). Копия повёрнута на 90° вокруг вертикальной оси, сплющена по
ширине шкафчика (локальная ось X) в тонкую пластину (2 % глубины) и растянута по глубине (ось Z) до ширины шкафчика, затем
сдвинута к открытой задней стороне (+Z, у стены; лицо шкафчика на −Z, §16.6) на 0,003 ед. внутрь. Боковая сторона копии
оказывается на месте спинки, с тем же рисунком и тем же «верхом»; остальное от копии плоское и лежит внутри шкафчика (по
высоте и ширине копия на 0,2 % меньше, чтобы края боков закрывали её). Копии записаны в список рендереров клетки
(`AddRendererReferences`), чанк показывает и прячет их вместе со шкафчиком. Имя `BackFace` не содержит слов, по которым
ищутся предметы. Первая версия (`e943301`) копировала лицевую сторону на спинку (поворот на 180°), это было не то.

**3. Student Shuffle и комната event spawner.** Комнату определяет `room.category == RoomCategory.EventSpawner`
(`room.offLimits` берётся из ассета комнаты и ненадёжен). Для предметов такие клетки — пустота: `FlightCell`
возвращает `null`, и бросок, пинок и дрейф не входят туда даже через открытую дверь; `TryPlace` и
`CanPlaceAtCurrentPosition` не ставят туда предмет; студент не ловит предмет, если стоит в такой клетке или коробка
предмета заходит в неё (`FindFollowerUnder`); едущий предмет, чья коробка заходит в такую клетку (`FxStepRide`,
`BoxTouchesEventSpawner`), остаётся на месте, падает и больше не едет (`RideBlocked`); выход из водоворота
выбирается не там (`TryPickWhirlpoolExit`).

**4. Гравитационный хаос на потолке.**

Правило (исправлено в §16.8): предмет, который несут, берёт гравитацию несущего. Игрок на потолке (`PlayerIsFlipped`,
событие активно): `UpdateHeldFacing` каждый шаг ведёт `CarryState.CarryRoll` к 180° (540°/с), к 0° у игрока на полу.
Поза в руках — `RolledCarryRotation`: прямая `CarryRotation`, повёрнутая на `CarryRoll` вокруг горизонтальной оси к игроку;
`TargetRotation` и `CarryRotation` не крутятся (посадка и `FlightBoxClear` ждут прямую позу). `ReleaseHeld` (не пинок)
сначала ставит тело точно в эту позу (`SnapCarryPose`), `FxOnRelease(state, kick)` кладёт в `EventFx` позу выпуска
(`BaseRotation`), уже набранный поворот (`RollOrigin` = `RollAngle` = `CarryRoll`) и ось (`RollAxis`) и пускает
предмет вверх, если игрок перевёрнут и событие активно. `FxApplyPose` поворачивает предмет на `RollAngle − RollOrigin`
вокруг `RollAxis`; целевой угол остаётся абсолютным (180° при гравитации вверх, 0° при обычной), поэтому в конце
события предмет сам поворачивается обратно и падает.

Наоборот: предмет, прилипший к потолку, берёт игрок на полу. `ResumeFromAir` берёт его позу как есть и поворот
`RollAngle`, расчёт «прямая поза + поворот» продолжает без скачка, и `UpdateHeldFacing` разворачивает предмет к 0°. После
выпуска он падает на пол. Игрок на потолке, взяв такой предмет, держит его вверх ногами.

Пинок: предмет остаётся как есть (`FxOnRelease(state, true)`): свои гравитация (`Pinned` или `GravityTarget < 0` — вверх) и
поза (повёрнутый предмет не выпрямляется, поэтому и не переворачивается заново). Поза посадки — прямая поза под поворотом
(`ResumeFromAir`). `KickVelocity(state, ray, fromCeiling)`: «от поверхности» для предмета на полу — вверх, для
прилипшего к потолку — вниз; если взгляд направлен в эту поверхность (игрок на потолке смотрит на пол), берётся
горизонтальный курс, `KickUpward` и `KickLift` добавляются в сторону от поверхности.

**5. Наводнение как в оригинале.** Предмет проходит те же шаги, что персонаж (`Whirlpool.Update` и
`Whirlpool.Teleport`), но выходит из одной из уже стоящих воронок:

1. Предмет на полу в 5 ед. от центра (`FxDrift` → `FxBeginSink`): водоворот закрывается (слой 19 и `Close()` —
   приватный, запускается рефлексией; `StartClose()` остановил бы все его корутины), поэтому на один водоворот
   приходится один предмет.
2. Выход (`TryPickOtherWhirlpool`): случайный из других водоворотов наводнения (`flood.whirlpools`), кроме
   закрывающихся (слой 19: использованные и выходы персонажей), и не в комнате event spawner. Этот водоворот
   остаётся открытым, его никто не закрывает. Только если других не осталось, делается, как в `Whirlpool.Teleport`:
   в случайной клетке (`AllTilesNoGarbage(false, false)`, копия списка, запасной вариант `(false, true)`; не комната
   event spawner; `ConvertEntityUnsafeCells`) создаётся новый водоворот (копия `whirlpoolPre`, `FormTime` = 3 с, слой 19,
   добавлен в `flood.whirlpools`), который закрывается, когда предмет вышел.
3. `FxStepSink`: предмет скользит к центру и за 0,4 с (`sinkSpeed` 2 · `EnvironmentTimeScale`, процент 1 → 0,2)
   опускается в пол на свою высоту + 0,3 (без сжатия масштаба: оригинал уменьшает высоту сущности, а у предмета
   пол всё скрывает), прыгает в центр выбранного водоворота, за 0,4 с поднимается (0,2 → 1) и садится, как любой
   брошенный предмет. Севший предмет лежит, лежащие предметы водоворот не тянет, поэтому обратно его не затягивает.
4. Если выхода нет совсем, предмет поднимается на месте. Если наводнение кончилось и водовороты уничтожены,
   предмет заканчивает путь по запомненным координатам. `FxAbortSink` (возврат на место, ошибка шага) закрывает
   новый водоворот, если он был создан. Удалены сжатие и рост масштаба (`PropFx` теперь только сплющивание).

**Проверка в игре.**

1. Загрузить 3-й этаж: сравнить время загрузки с прежним.
2. Взять красный и синий шкафчик (G), обойти сзади: на месте задней стенки боковая сторона шкафчика (не дверь, не
   дыра); поставить, перенести ещё раз, пнуть: стенка остаётся и видна вместе со шкафчиком (не мигает при смене
   чанка). Размеры коробки в строке лога `got a back` для сверки осей.
3. Student Shuffle: бросить и пнуть предмет к двери комнаты event spawner: он не заходит внутрь; предмет на голове
   студента, который идёт в комнату, остаётся у двери и падает.
4. Гравитационный хаос: перевернуться (фигура), взять предмет с пола: он в руках переворачивается к потолку; выпустить
   (ЛКМ) или бросить (ПКМ) — он падает вверх и прилипает к потолку. На потолке взять потолочный предмет — он в руках
   остаётся вверх ногами. Игроку на полу взять потолочный предмет: он в руках разворачивается, выпущенный падает на пол.
   Пнуть предмет колёсиком (на потолке и на полу, в том числе глядя на пол): он летит вдоль взгляда, а не в пол;
   предмет на потолке при пинке не разворачивается.
5. Наводнение: бросить предмет в водоворот: тот сжимается и пропадает, предмет уходит в пол и выходит из другого
   водоворота, который остаётся; второй предмет в исчезнувший водоворот уже не тянется. Когда остался один водоворот,
   предмет выходит из нового, случайно созданного.

**Ограничения и риски.**

- Расчёт «причина загрузки — поиск по сцене каждый кадр» сделан по коду. Если после правок загрузка всё ещё долгая,
  нужен профайл (что ещё работает во время генерации).
- Спинка шкафчика — боковая сторона, растянутая по глубине до ширины (пропорционально ширина/глубина, обычно 2:1); оси
  шкафчика (ширина по X, спинка на +Z) взяты из `LockerBuilder` и §16.6, меш не читался. Если спинка не на месте, строка
  лога `got a back` покажет размеры коробки. Для нестандартного меша зазоры 0,2 % могут дать щель или мерцание —
  менять `LockerBackScale`, `LockerBackThickness`, `LockerBackGap`.
- Гравитация предмета в руках — по гравитации игрока, не по самому предмету; предмет высотой с комнату не переворачивается
  (потолка для него нет), его выпускают вниз. Первая версия (`e943301`, предмет с пола у перевёрнутого игрока падал на
  пол) была неверным прочтением запроса.
- Выход через уже стоящую воронку — не то, что делает ваниль (там для персонажа создаётся новая временная воронка в
  случайной клетке): так выбрано по просьбе. Воронки расходуются по одной на предмет; когда осталась последняя,
  работает ванильный вариант с новой воронкой.
- Предмет без свободного места на выходе садится по обычному правилу посадки (`TryPlaceNearby`), иначе
  возвращается на исходное место.

### 16.9 Пятый отчёт: водовороты, студенты, фигуры, Balder, супер-двери «мёртвые»

**Причина.** Чтобы убрать поиск по сцене (§16.7 п. 1), в `f508228` я заменил `FindObjectOfType` в реестрах событий на

других причин, по которым мертвы сразу все функции, в коде нет. Кроме того, все реестры и тики (сплющивание, обход
персонажей) жили в одном `try`: ошибка в одном шаге отключала все остальные каждые 0,5 с. Список супер-дверей брался один
раз за этаж и отбрасывал двери с `door.ec != этаж`.

**Что сделано** (`g.Events.cs`, одна правка `g.cs`).

1. `RefreshFloorEvents`: события этажа — дети `ec.transform` (там их создают строитель уровня и `StartEvent`; у среды
   несколько сотен детей: комнаты, строители, персонажи; тайлы не дети) и приватный `EnvironmentController.events`
   (рефлексия). Список берётся заново, когда меняется число детей, и не реже раза в 5 с (`FloorEventsRescanSeconds`).
   Поиска по сцене нет.
2. `RunningEvent<T>`: идущее событие вида `T` — то, что вернул `GetEvent`, иначе событие из списка с `Active == true`
   (`Begin()` ставит флаг, как бы событие ни запустили). От него: `_gravityEvent`, `FloodEvent.whirlpools`,
   `GravityEvent.flippers`, дети `StudentEvent`. Остальное как в `2cd5a89`: магнит, сток, поездка на голове, фигуры.
3. Супер-двери: собственный список `LockdownEvent.doors` (рефлексия) плюс список дверей этажа; `EnsureLevelDoors` теперь
   отбрасывает только двери чужой среды (с пустым `ec` оставляет, как раньше). Объём Balder — `Entity.Trigger`
   (триггер, по которому игра сама сплющивает), запасной вариант — коллайдеры на объекте.
4. Каждый шаг в своём `try`: список событий, гравитация, наводнение, студенты, персонажи, супер-двери; пинок, сплющивание,
   обход персонажей; три сплющивателя (Balder, молоток, двери) тоже по отдельности. Ошибка пишется в лог отдельной
   строкой на вид (не чаще раза в 5 с), остальные шаги работают.
5. Предмет, брошенный в фигуру переворота: реестр фигур теперь заполняется при любом запуске, `FxTouchFlippers`
   срабатывает, предмет переворачивается, берёт гравитацию «вверх» или «вниз», прилипает к потолку (твёрдый) и берётся
   (G, колёсико): правило §16.7 п. 4 и §16.8 п. 1 для предмета, взятого и поставленного игроком на потолке, не менялось.

**Лог** (§16.3): `Events of this floor: …`, `<событие> is running.` / `is over.`, затем уже знакомые `Flood: whirlpools: N found.`,
`Gravity Chaos: gravity flippers: N found.`, `Student Shuffle: students: N found.`, `A whirlpool pulls …`. Если событие
идёт, а строки `is running.` нет, мод его не нашёл: тогда нужны строка `Events of this floor` и строки `Event handling (…) failed`.

**Проверка в игре.** Запустить наводнение, гравитационный хаос, Student Shuffle, Balder Dash и Lockdown и таймером,
и из Level Studio. В логе `X is running.`; бросить предмет к водовороту (его тянет, он тонет и выходит из другого), в
фигуру (переворачивается, прилипает, берётся), к толпе (едет на голове), под валун и под закрывающуюся супер-дверь
(сплющивается).

**Ограничения.** Событие, которое лежит не под `ec.transform` и не в `EnvironmentController.events`, мод не найдёт.
Магнит тянет брошенные, выпущенные и пнутые предметы, лежащие не тянет (как и в `2cd5a89`).
