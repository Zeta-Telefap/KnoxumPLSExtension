# Build Mode / Builder Garage — дизайн-документ (черновик)

Статус: **дизайн обсуждается; BepInEx entry point `c` и прототип переноса `g` написаны, но не собраны и не проверены в игре**. Все числа и решения ниже помечены как «предлагается» и могут быть изменены.
Связанные документы: `CONTEXT.md`, `IDEAS.md`, `BUGS_AND_NEXT_STEPS.md`.
Подробный порядок написания механик: [`BUILD_MODE_IMPLEMENTATION_PLAN.md`](BUILD_MODE_IMPLEMENTATION_PLAN.md).

---

## 1. Идея в одном абзаце

Игрок может переставлять мебель (автоматы, шкафы, столы), двигать и сносить стены и двери
(синие стандартные / жёлтые распашные), а также пристраивать к школе новые комнаты
модулями 1x1 … 3x3. Товары Builder Garage — мебель, стены, двери и модули комнат —
покупаются за **YTP**. Ресток ассортимента оплачивается отдельно: игрок сдаёт в магазин
собранные объекты интерьера и стены.

## 2. Ключевые решения (черновые, «предлагается»)

| Вопрос | Черновое решение | Почему |
|---|---|---|
| Взаимодействие | **Всё в реальном времени, без паузы NPC** — правки не останавливают игру | Решение пользователя: стройка идёт «на ходу», Балди продолжает охоту |
| Перетаскивание | **G — поднять; ЛКМ — поставить; ПКМ во время переноски — бросить** в стиле Gravity Gun | Решение пользователя; переносимый объект удерживается перед камерой, бросок — физический |
| Покупка товаров | **YTP** за мебель, стены, двери и модули комнат | Все товары магазина имеют прямую цену в YTP |
| Ресток | Сдача собранных объектов интерьера и стен; за ресток также начисляются YTP | Сдача расходует собранное, а успешное обновление ассортимента даёт бонусные очки |
| Builder Garage | **Физическая комната** в свободном углу сетки + дверь из коридора | Сохраняет «зайти внутрь»; UI-вариант остаётся запасным |
| Граница уровня | Строим **только внутри существующей сетки** | `ec.cells` фиксированного размера; расширение наружу — отдельный проект |
| Собранное для рестока | Отдельный счётчик мода; ванильные 3 слота не трогаем | Снесённые объекты/стены сдаются магазину при обновлении ассортимента |
| Где живёт код | Отдельный класс/модуль + своя секция конфига, **не внутрь Chaos Mode** | Иначе второй файл на 3000 строк |

**Переноска через двери:** объект открывает незапертую дверь при касании её коллайдера или
меша, пользуясь штатным `Door.OpenTimed`. Если ширина стороны, захваченной при нажатии G,
превышает ширину одной клетки BB+ (10 мировых единиц), объект не открывает дверь; уже
открытая дверь закрывается заранее, если игрок ещё не у проёма. Запертые двери мод не отпирает.

## 3. Техническая база (по декомпилу `ultimate_dev_mods_decompile.cs`)

### 3.1 Клетки и стены

- **Стена — не объект.** Стена = биты покрытия граней клетки (`Cell.constBin`) + меш тайла
  `ec.TileMesh(constBin)` + коллайдеры `tile.Collider(dir)`. Отдельного GameObject стены нет.
- `ec.CloseCell(pos, dir)` — поставить грань (стену) с одной стороны.
- `ec.ConnectCells(pos, dir)` — убрать грань, открыть проход.
- `ec.UpdateCell(pos)` — пересчитать `constBin` по соседям (кто чья комната) → стены «сами»
  перерисовываются после смены принадлежности клетки.
- `ec.CreateCell / DestroyCell / SwapCell / MergeCell / RefreshCell` — низкоуровневые операции.
- `Cell.WallHardCovered(dir)`, `Cell.WallAnyCovered(dir)`, `Cell.HardCover/HardCoverWall/SoftCover` —
  проверка и установка покрытия.
- `Cell.SetShape()` внутри вызывает `ec.RecalculateNavigation()` + `GameCamera.RecalculateDijkstraMap()`
  → **дорого**, нужен батчинг (см. §5).

### 3.2 Комнаты

- `RoomAsset` (`ScriptableObject`): `cells: List<CellData>` (`pos` + `type`-бин), текстуры
  `florTex / wallTex / ceilTex`, `potentialDoorPositions / forcedDoorPositions`,
  `offLimits`, `eventSafeCells`, `standardLightCells`, `lights`, `spawnWeight`.
- `RoomAsset` собирается в рантайме: `ScriptableObject.CreateInstance<RoomAsset>()`.
- `LevelBuilder`:
  - `LoadRoom(asset, position, roomPivot, direction, lockTiles)` — построить комнату;
  - `LoadIntoExistingRoom(...)` — догрузить ассет в существующую комнату;
  - `ExpandArea(room, direction)` — расширить комнату на 1 клетку в сторону;
  - `DestroyRoom(room)` — снести комнату целиком;
  - `ManuallyBuildDoor(room, doorPre, pos, dir)` / `BuildDoorIfPossible(...)`;
  - `BuildWindowIfPossible(...)`;
  - `InstatiateEnvironmentObject(prefab, cell, dir)`.
- `RoomController.UpdatePosition()` пересчитывает bounds по клеткам; `room.cells`,
  `room.connectedRooms`, `room.roomsFromHall`.
- `RoomController.GenerateTextureAtlas()` → `ec.GetMatchingTextureAtlas(...)` **дедуплицирует**
  атласы по тройке текстур, так что наследование текстур хозяина не жрёт память.

### 3.3 Двери, стены-объекты, мебель

- `Door : TileBasedObject` — поля `ec`, `position`, `direction`, `bOffset`.
  `StandardDoor` (синяя), `SwingDoor` (жёлтая, две створки в wall slot).
- `ec.SetupDoor(door, cell, dir)` + `door.Initialize()` — поставить дверь в готовую клетку.
- `EnvironmentObject` — часть мебели/интерактивных объектов: `coverage` (`CellCoverage`) +
  `tileShapeMask` + коллайдеры. Живёт под `room.objectObject`; клеточное покрытие надо переносить
  вместе с объектом.
- Не вся мебель — `EnvironmentObject`: декомпил `DeskBuilderStandard` и `LockerBuilder`
  показывает столы/стулья и шкафчики, создаваемые как `MeshRenderer` под комнатой или
  `Cell.ObjectBase`. Механика `g` обрабатывает такие renderer-модели по имени объекта.
  `SodaMachine` — `EnvironmentObject`.
- `TileBasedObject` (не двери) двигаются строго по сетке: `position` + `direction` и не входят
  в первую версию переноски.

### 3.4 Экономика и UI

- `Pickup` (`IClickable<int>`): `price`, `OnItemPurchased / OnItemDenied / OnItemCollected`,
  `AssignItem(ItemObject)`, `showDescription`, `repeatable`; можно использовать как образец
  продажи товаров за YTP.
- Механизм `Pickup` с `item == NoneItem` забирает предмет из выбранного слота игрока —
  полезный образец для сдачи собранного объекта при рестоке.
- `ItemManager`: `defaultInventorySize` (3) + стикеры, `AddItem / RemoveItem / items[]`.
- `StoreRoomFunction` + `StoreScreen` — рабочий образец магазина с рестоком
  (`PurchaseRestock`, `Restock`, `ItemPurchased`, Johnny-аудио); интерфейс магазина можно
  переиспользовать, заменив оплату ассортимента на сдачу собранных объектов/стен.
- `WeightedSelection<T>` — пул ассортимента.

### 3.5 Карта, свет, навигация

- `Map`: `tiles: MapTile[,]`, `foundTiles: bool[,]` создаются при старте → новым клеткам нужны тайлы.
- `ec.GenerateLight / RegenerateLight / QueueLightControllerForUpdate / UpdateLightingAtCell`;
  `ec.lightMap[x, z].RegenerateLightSources()` вызывается в `SwapCell` автоматически.
- `ec.RecalculateNavigation()`, `ec.BuildNavMesh()`, `ec.QueueDijkstraMap(map)`.
- `ec.CullingManager.UpdateChunk(chunkId)` — чанки строятся под `levelSize`.

## 4. Ограничения и риски

1. **Фиксированная сетка.** `ec.cells = new Cell[levelSize.x, levelSize.z]` и массивы `Map`
   создаются один раз. Пристройки — только в свободные клетки внутри уровня.
2. **Navmesh / Dijkstra.** Любая правка формы клетки тянет пересчёт навигации → фризы.
   Нужна модель-черновик + один коммит.
3. **Свет.** Новые клетки без источников — чёрная дыра. Нужны `standardLightCells`/`GenerateLight`.
4. **Карта (M).** Без новых `MapTile` пристройки не видно на миникарте.
5. **`ec.rooms` = спавн.** События/предметы/NPC выбираются по комнатам → новой комнате нужны
   `offLimits = true` и `eventSafeCells`.
6. **Сущности в клетке.** Удаление клетки с NPC/игроком или двери, в которую идут, — риск NRE.
   Нужна проверка «здесь кто-то есть — операция запрещена».
7. **Сохранения.** Игра сохраняется между этажами; постройки исчезнут без своего оверлея
   (файл мода, ключ = seed + этаж).
8. **Атласы.** Каждая новая тройка текстур = отдельная текстура атласа (дедуп есть, но не бесплатен).
9. **Масштаб.** 1 клетка = 10×10 юнитов; обычный класс — несколько десятков клеток.
   1x1 — чулан. Ходовые размеры: 2x2, 2x3, 3x3, 3x4.
10. **Активити/ноутбуки.** Пристройка не должна создавать `Activity` — иначе ломается прогресс Балди.

## 5. Режим «на ходу» — что это меняет

Игра не ставится на паузу: NPC ходят, Балди охотится, двери открываются, пока игрок
переставляет стол. Это возможно, но меняет архитектуру: **никакой «черновой» геометрии**,
которая живёт в мире до коммита, и **никаких многокадровых правок без защиты**.

### 5.1 Три правила

1. **Превью — не геометрия.** Призрак стены/двери/мебели рисуется отдельным объектом
   с выключенными коллайдерами. Мир (`ec.cells`) меняется только в момент подтверждения.
2. **Одна правка = один атомарный коммит в одном кадре.** Внутри коммита:
   `ec.FreezeNavigationUpdates(true)` → все операции с клетками → `FreezeNavigationUpdates(false)`.
   `RecalculateNavigation()` при заморозке — no-op (проверено в декомпиле), поэтому
   батч из 10 операций даёт **одну** пересборку, а не 10.
3. **Сначала проверка, потом изменение.** `DryRun()` до применения: свободны ли клетки,
   нет ли NPC/игрока/предмета, не занята ли дверь, не отрежет ли это путь
   (`ec.CheckPath`/`NavigableDistance` до коммита).

### 5.2 Опасные места в реальном времени

| Операция | Риск | Защита |
|---|---|---|
| Удаление стены/клетки | NPC/игрок внутри → провал сквозь пол или NRE | Проверка `ec.Npcs`, `ec.Players` по клетке; запрет или «выталкивание» |
| Удаление двери | Дверь в процессе открытия/прохода NPC | `Door` занята → отказ, `bOffset`/створки проверять отдельно |
| Закрытие стены | Отрезает NPC от пути → он застревает | `CheckPath` из позиции каждого NPC в его цель; отказ, если путь рвётся |
| Снос мебели | В объекте стоит NPC / это укрытие | Проверка `Cell`-ссылок и `coverage` перед удалением |
| Пристройка комнаты | Десятки клеток + свет + карта + navmesh = фриз | Сборка по кадрам в корутине (см. §5.3) |

### 5.3 Пристройка комнаты по кадрам

Полная сборка комнаты — это `LoadRoom` + свет + `MapTile` + navmesh, и в один кадр это
даст заметный хитч. Предлагается «стройка» как процесс:

1. Игрок подтверждает пристройку → клетки помечаются `Cell.locked = true` и получают
   визуал «строительных лесов» (или полупрозрачный пол).
2. Корутина раз в N кадров применяет порцию (по 1–2 клетки), между порциями — `yield`.
3. По завершении: освещение, `MapTile`, один `BuildNavMesh()`, снятие `locked`.
4. **Стройка шумит:** `ec.MakeNoise(pos, value)` на каждую порцию → NPC идут на звук.
   Это и баланс, и фича: строишь — рискуешь.

Такой же паттерн уже используется в игре при генерации уровня (`TicksAtBeginningOfFrame`
+ `frameTickLimit`), то есть подход не противоречит движку.

### 5.4 UX без паузы

- Всё на горячих клавишах, без модальных окон: выделил → действие → подтвердил.
- Игрок может двигаться с объектом перед камерой: G поднимает его, ЛКМ ставит на ближайшую допустимую клетку под прицелом, ПКМ бросает физически.
- Отмена (undo) работает мгновенно и так же атомарно.
- Индикаторы в HUD: баланс YTP, собранные для рестока объекты/стены, «руки заняты», «здесь нельзя строить» с причиной.
- Ошибки объясняются одной строкой («NPC в клетке», «перекроет проход», «нет материала»),
  а не молчанием.

## 6. Архитектура (предлагается)

Разделение на **модель** и **применение**:

```
BuildModel (свои данные)   →  DryRun()  →  ApplyChanges()  →  EnvironmentController / LevelBuilder
- очередь правок                          (FreezeNavigationUpdates(true) → операции →
- undo-стек                                FreezeNavigationUpdates(false), один кадр)
- счётчик собранных объектов/стен для сдачи при рестоке
```

Никакого «режима» как отдельного состояния игры: инструмент всегда доступен, паузы нет.
`BuildModeController` — это скорее «активный инструмент + очередь правок», а не экран.

Целевое разделение файлов (entry point `c` и прототип переноса `g` уже созданы):

```
src/BuildMode/BuildModeController.cs   // вход, режим, коммит
src/BuildMode/BuildModel.cs            // черновик правок + undo
src/BuildMode/WallTool.cs              // грань: поставить/убрать/снести
src/BuildMode/DoorTool.cs              // синие/жёлтые двери
src/BuildMode/Plugin/c.cs              // BepInEx entry point
src/BuildMode/Tools/g.cs               // G захват, ЛКМ установка, ПКМ физический бросок
src/BuildMode/RoomBlueprint.cs         // RoomAsset из шаблона 1x1…3x3
src/BuildMode/RestockCollection.cs    // учёт собранных объектов и стен
src/BuildMode/BuilderGarage.cs         // магазин, покупки за YTP, сдача на ресток
src/BuildMode/BuildModeHUD.cs          // оверлей/призрак/подсказки
src/BuildMode/BuildModeInspector.cs    // dev-инспектор (этап 0)
```

Конфиг (BepInEx, отдельная секция `BuildMode`):
`Enabled`, `CountDemolishedForRestock`, `MaxRoomSize`, `GarageSpawnChance`,
`RestockCostItems` (1–3), `AllowGridGrowth` (false), `BuildNoise` (сила шума при стройке),
`RoomBuildFrames` (за сколько порций собирается пристройка), `ProtectPaths` (true — не рвать путь NPC).

## 7. Экономика и ресток (черновик правил)

**Покупки — за YTP.** Игрок тратит YTP на любые товары Builder Garage: мебель, панели
стен, двери и модули комнат. У каждого товара своя цена в YTP; цены и баланс будут
настраиваться после игрового тестирования.

**Ресток — за собранные объекты и стены, с наградой в YTP.** Чтобы обновить ассортимент,
игрок сдаёт магазину добытые при разборе объекты интерьера и стены. После успешного
рестока игрок дополнительно получает YTP; эти очки остаются валютой для покупок товаров.
Сдача не заменяет оплату YTP за покупку. Ванильные слоты инвентаря не используются как
постоянное хранилище: собранное учитывается отдельным счётчиком/пулом мода и расходуется
при рестоке.

| Что собрано | Учитывается для рестока |
|---|---|
| Снесённая стена | 1 единица стены/материала |
| Снесённый предмет интерьера | 1 единица объекта |
| Убрана дверь | 1 единица объекта (предварительно) |
| Разобрана пристройка | материалы учитываются по её составу (правило возврата уточнить) |

**Черновое правило:** один ресток требует сдать 1–3 собранные единицы — объекты,
стены или их сочетание. Конкретное количество и влияние ценности сданного на качество
нового ассортимента пока не зафиксированы.

**Цена временем и шумом.** Так как игра не встаёт на паузу, у каждой операции есть вторая
цена — внимание NPC: снос стены, перенос мебели и особенно сборка пристройки вызывают
`ec.MakeNoise(pos, value)`. Строить под носом у Балди дорого не только YTP и материалами,
но и нервами.

## 8. Этапы реализации

| Этап | Что | Зачем | Критерий готовности |
|---|---|---|---|
| 0 | **Dev-инспектор**: оверлей «клетка/стена/дверь/объект под прицелом» + поля + лог | Без него гадаем, почему меш/бин не тот | Видно `constBin`, `room`, покрытие, `TileBasedObject` |
| 1 | **Снос/восстановление стены и двери** | Проверяет `UpdateCell/ConnectCells`, свет, карту, navmesh | Снёс стену в игре → нет фриза, никто не застрял, карта цела |
| 2 | **Инструмент правки без паузы**: сетка, призрак, атомарный коммит, undo | База для всего остального | Правка применяется в одном кадре, NPC не застревают, отмена работает |
| 3 | **Перенос мебели** | Самая частая операция | Объект переносится, `coverage` обновлён, NPC обходит |
| 4 | **Строительство стен/дверей** | Проверяет установку геометрии; затем товар оплачивается в Builder Garage за YTP | Поставил стену/дверь, всё проходимо; бесплатный debug placement отключён в релизе |
| 5 | **Пристройки-комнаты** (`RoomAsset` из шаблонов) | Ядро идеи | Новая комната со светом, картой, дверью, без событий |
| 6 | **Builder Garage + покупки за YTP + ресток** | Экономика | Товары покупаются за YTP; сдача собранного обновляет ассортимент и начисляет бонусные YTP |

Порядок сознательно от дешёвого к дорогому: каждый этап играбелен и проверяем,
и любой этап можно «поправить», не переделывая предыдущие.

## 10. Захват предметов (`g`): как выбирается цель

**Принцип: подсвеченный предмет — это ровно тот предмет, который поднимет G.** Подсветка и клавиша
берут цель из одного запроса, который выполняется раз в кадр (`ResolveAimThisFrame`). Опроса по
таймеру, «липкости» и повторного поиска в момент нажатия больше нет.

**Правила выбора (по порядку):**

1. Луч идёт из камеры по центру экрана (`RaycastNonAlloc`, дальность 16, триггеры игнорируются),
   попадания сортируются по расстоянию. Игрок и предметы в полёте после броска не считаются ни целью,
   ни преградой.
2. **Первая твёрдая поверхность решает.** Если это коллайдер поднимаемого предмета — он и есть цель.
   Если это стена, дверь, окно, NPC или предмет, который нельзя носить, он закрывает всё, что за ним:
   сквозь геометрию ничего не поднимается.
3. **Помощь прицеливания.** Предмет, которого луч физически не коснулся (нет коллайдера или в
   коллайдере дыры, например открытая спинка стула), ищется по мешам: луч проверяется против
   локального бокса каждого меша (а не против раздутого `renderer.bounds`). Предмет без коллайдера
   соревнуется с физическим попаданием по расстоянию. Предмет с коллайдером подключается, только если
   луч не попал в другой поднимаемый предмет. Во всех случаях предмет должен быть ближе первой твёрдой
   поверхности. Реестр таких предметов строится порциями (~1 мс за кадр) и обновляется при смене уровня
   и раз в 20 секунд.
4. Приоритет над `g2`: если под прицелом есть предмет, структурная подсветка (стены/двери/окна)
   гасится, а G достаётся предмету. Структуры берутся, только когда предмета нет.

**Что нельзя поднимать** (`ForbiddenPickupReason`): лифты, предметы-`Item`, облака (`CoverCloud`),
всё, внутри чего есть настоящий источник света (лампы, светильники), и имена с подстроками
`elevator`, `lift`, `lamp`, `light`, `chandelier`, `sconce`, `bsoda`, `no squee`, `covercloud`,
`chalkcloud`. Собственное свечение мода (объект `Carry placement glow`) в эту проверку не входит.

**Почему раньше «через жопу»:** подсветка добавляла предмету дочерний `Light`, а проверка «нельзя
поднимать» отвергала любой корень с дочерним `Light`. Подсвеченный предмет становился «запрещённым»:
подсветка мигала, G на подсвеченном предмете отказывала («Highlighted pickup is no longer
available»), а нажатие поглощалось. К этому добавлялись опрос подсветки раз в 0.25 с с запасом 0.35 с
и гистерезисом, три независимые точки входа для G и запасной поиск по раздутым AABB без учёта
преград.

**Диагностика (строки лога `BepInEx/LogOutput.log`):**

## 11. Двери, мини-карта и бросок предметов (`g2`, `g`)

Код этого раздела **не собирался и не запускался в игре**: проверены только синтаксис (tree-sitter),
арность вызовов и то, что каждый используемый член существует в декомпиле BB+.

### 11.1 Двери: куда поставил, там и стоит

**Принцип.** Дверь встаёт ровно на ребро, показанное превью, и стена на этом ребре исчезает **с обеих
сторон**. Что станет со старым ребром, когда дверь уйдёт, описано в §12.2: стена, которую снимала эта
дверь, возвращается теми же гранями; проём, где дверь стояла с самого начала, остаётся открытым.
(Прежнее правило «старый проём всегда открыт» и константа `SealOldDoorway` удалены.)

**Что было не так** (все причины проверены по коду BB+):

| Причина | Откуда |
|---|---|
| После `SetupDoor` мод вызывал `UpdateCell` для четырёх клеток. `UpdateCell` не ставит стену только на грани из `doorDirs` клетки, но `AssignDoor` кладёт в `doorDirs` **обеих** клеток одно и то же направление (у дальней клетки это направление «от двери»). На границе комнат дальняя клетка получала стену на грани к двери: односторонняя стена в новом проёме | `EnvironmentController.UpdateCell` (69032), `SetupDoor` (70632), `Cell.AssignDoor` (55870) |
| Тот же `UpdateCell` для старого проёма возвращал там стену, а у дальней клетки из-за устаревших записей пропадала её **другая** стена | то же |
| `RemoveDoorReferences` убирал по одному направлению на клетку и оставлял устаревшие записи в `doorDirs`/`doorDirsSpace` | `g2.cs` |
| `SynchronizeDoorBlocking` после переноса делал `Block(true)`+`Block(false)` уже на **новых** клетках, а счётчики старых оставались: у запертой двери старый проём навсегда оставался заблокированным для навигации | `Door.Block` кэширует значение (63082) |
| `Door_SwingingOneWay.Initialize` сам ставит односторонний блок, а мод ставил его ещё раз вручную: двойной счётчик | `Door_SwingingOneWay` (63431) |
| Мини-карта: `SwingDoor.Initialize()` (и `FacultyOnlyDoor`, `LockdownDoor`) при **каждом** вызове создаёт новую пару маркеров, старая остаётся. У `StandardDoor` маркеры создаёт только приватный `Start()`, поэтому после переноса они оставались на старом месте. Стены на уже открытых плитках карты вообще не перерисовывались: `Map.Find` вызывается один раз | `SwingDoor` (115642), `StandardDoor` (109138), `Map.UpdateTile` (90145) |

**Как теперь устроен перенос** (`CommitDoorMove`, порядок важен):

1. Пока дверь ещё «стоит» на старом ребре: `door.Block(false)`, снятие одностороннего блока, удаление её
   маркеров мини-карты (`ClearDoorMapMarkers`, находит поля `MapTile` рефлексией по всей цепочке типов;
   окна пропускаются, их маркеры ведёт `UpdateWindowMap`), `UnregisterDoorFromCell` для обеих клеток.
   Он **пересобирает** `doors`, `doorDirsSpace`, `doorDirs`, `doorHere` из оставшихся дверей клетки.
2. Старое ребро: записанная стена возвращается, окно без записи закрывается стеной, остальной проём
   остаётся открытым (§12.2).
3. Новое ребро: `ConnectCells` с обеих сторон, затем `SetupDoor`. **`UpdateCell` для рёбер дверей больше
   не вызывается.** После регистрации `EnsureDoorEdgeOpen` проверяет, что стены на ребре нет.
4. `InitializeMovedDoor`: `StandardDoor` не получает повторный `Initialize()` (он подписал бы дверь на
   события второй раз) и не получает `Start()`; вместо этого `RefreshStandardDoorTextures` повторяет первую
   половину `Start()` (текстуры стен и материалы проёма по новым комнатам), а `EnsureDoorMapMarkers`
   создаёт ровно одну пару маркеров (спрайт по `locked`, цвет комнаты, `ToUiRotation`). Семейство
   `SwingDoor` вызывает `Initialize()` один раз: старые маркеры к этому моменту уже удалены.
5. `RefreshMapTiles` перерисовывает четыре плитки карты (`Map.UpdateTile`).
6. Откат и отмена зеркальны: блок снимается, маркеры удаляются, регистрация на цели снимается,
   `RestoreCellSnapshots`, дверь возвращается на исходное ребро с одной парой маркеров. Поля маркеров
   никогда не остаются `null` (`LockdownDoor.UnInitialize` разыменует их).

**Перенос стен.** Те же четыре `UpdateCell` в `CommitWallMove` заменены на `UpdateCellSafely`: на время
вызова `doorDirs` клетки подменяется её собственным видом на свои двери, затем восстанавливается. Без
этого стена, переставленная рядом с дверью, заделывала бы проём. Для клеток без дверей поведение прежнее.
После переноса стены тоже обновляются плитки мини-карты.

**Лог (`BepInEx/LogOutput.log`):**

| Строка | Значение |
|---|---|
| `Door move (<Тип>): (x, z)/Dir -> (x, z)/Dir; old edge: <что с ним стало>; wall removed at the new edge: True; minimap markers replaced: 2.` | перенос выполнен; варианты `old edge: …` см. в §12.4; `2` — пара старых маркеров удалена |
| `A wall was still standing in the new doorway … removing it.` | не должна появляться; если появилась, что-то вернуло стену, и она убрана принудительно |
| `Structural target moved to …` | общая строка успеха (как раньше) |
| `Structural drag failed; restoring source` / `Door rollback failed` | исключение при переносе / при откате |
| `Door texture refresh failed` / `Minimap tile refresh failed` | некритичные сбои (перенос не отменяется) |

### 11.2 Бросок (ПКМ): стены и комната приземления

**Почему объект «появлялся не там».** `SettleThrown` определял комнату по **игроку**: если предмет
приземлялся в другой комнате, его переносили в ближайшую клетку комнаты бросающего («держим по свою
сторону стены»). Кроме того, `TryPlace` требовал, чтобы игрок мог дойти до клетки приземления.
Теперь **брошенный** предмет остаётся там, где остановился, даже в комнате, куда игрок не попадает;
проверяется только физическая свободность места. Брошенный через окно предмет разбивает окно и
остаётся в соседней комнате. Предмет, **выпущенный ЛКМ** (`DropHeld`), сохраняет прежнее правило
«комната игрока».

> **Заменено в §12.1.** Ниже описана версия с `BoxCast` поверх динамического `Rigidbody`: она не давала
> гарантии (пропускала начальные пересечения, углы, пол и потолок). Правила места приземления (первый
> абзац этого подраздела) остались в силе.

**Почему предметы летели сквозь стены.** Брошенный предмет — обычный динамический `Rigidbody`: столкновение
со стеной зависит от матрицы слоёв проекта, а она пропускала его насквозь. Прежнее «подтягивание в комнату
игрока» скрывало это, но не лечило. Теперь `FixedUpdate` перед каждым шагом физики проводит `BoxCast` по
скорости каждого летящего предмета (запросы матрицу слоёв не используют) и отражает скорость от первой
твёрдой поверхности (упругость 0,35, трение 0,85, зазор 0,04). Особые случаи: окно разбивается тем же
вызовом `Window.Break(false)` и предмет летит дальше (неразбиваемое окно — стена); незапертая дверь, в
проём которой предмет проходит по ширине, открывается (`OpenTimed`), запертая дверь или слишком широкий
предмет отскакивают; пол и потолок (нормаль почти вертикальна), сам предмет, игрок и любые `Entity` не
считаются преградой.

**Лог:**

| Строка | Значение |
|---|---|
| `Thrown prop hit <путь коллайдера> (layer N, prop layer M, …) at X u/s; bounced.` | **устарело**: новые строки о ударах см. в §12.4 |
| `Prop '<имя>' thrown came to rest in <комната> (<категория>), cell (x, z); the player is in <комната>; wall impacts on the way: N.` | итог: где предмет остался |
| `No free spot for the prop near … it went back to where it came from.` | в комнате приземления нет свободного места: возврат на исходное |
| `A prop was still airborne after 8 s` | предмет не приземлился за 8 с |
| `Thrown-prop wall sweep failed` | **устарело**: теперь `Thrown-prop flight step failed` (§12.4) |

### 11.3 Проверка в игре

1. **Дверь на чужую стену.** Возьмите дверь (G), поставьте на стену другой комнаты (ЛКМ). Ожидается: стены
   на ребре нет с обеих сторон, дверь стоит там, где было превью, проходить можно в обе стороны. В логе
   `Door move … wall removed at the new edge: True`.
2. **Старое ребро** зависит от того, что там было до двери: см. §12.2.
3. **Мини-карта** (до и после, повторить перенос 3 раза): маркеры двери только на новом месте, старых нет,
   пара ровно одна. Стены на плитках карты соответствуют реальным.
4. **Запертая дверь:** после переноса старый проём не блокирует навигацию, новое место блокирует.
5. **Стена рядом с дверью:** переставьте стену, примыкающую к двери: проём двери остаётся открытым.
6. **Отмена** (`Esc`) возвращает дверь и не трогает маркеры.
7. **Бросок в стену** (ПКМ): предмет отскакивает и падает у стены; в логе `Thrown prop hit …`.
8. **Бросок через окно:** окно разбивается, предмет остаётся в соседней комнате (`came to rest in`
   показывает другую комнату, чем `the player is in`).
9. **Бросок в дверь:** незапертая открывается и пропускает, запертая отбрасывает.

### 11.4 Ограничения

- Всё в §11 проверено только статически (см. начало раздела).
- Ограничения полёта (стены, пол, потолок, `BoxCast` по мебели): см. §12.5. Для повёрнутых предметов
  по-прежнему используется AABB рендереров (запас консервативный).
- Брошенный предмет может остаться в закрытой комнате, куда игрок не дойдёт: так задумано.
- Ванильные окна, ни разу не двигавшиеся модом, не записаны в `cell.doors`, поэтому дверь всё ещё можно
  поставить на ребро с ванильным окном (поведение не менялось).
- Стена, возвращённая на старое место, может отрезать часть комнаты (§12.5): её можно снова убрать
  инструментом стен.

## 12. Бросок без проходов сквозь стены и пол; стены возвращаются под дверью (`g`, `g2`)

Код этого раздела **не собирался и не запускался в игре** (в песочнице нет .NET и DLL игры). Проверен только
статически (синтаксис, вызовы, существование членов игры по декомпилу BB+) и на Python-моделях логики; модели в
репозиторий не включены.

### 12.1 Бросок (ПКМ) и выпуск (ЛКМ): собственный полёт вместо физики Unity

**Что было не так в §11.2.** `BoxCast` поверх динамического `Rigidbody` не видел стену, если предмет уже
касался её на старте (бросок вплотную), проверял уменьшенную коробку и скорость до шага физики, пропускал пол
и потолок. У пола нет горизонтального коллайдера, а у края карты предмет улетал в пустоту до таймаута в 8 с.

**Что сделано.** Предмет стал кинематическим телом, и двигает его только `StepFlight` (каждый `FixedUpdate`);
физика Unity в полёте не участвует:

- старт: ПКМ — `PlayerVelocity·0,35 + направление·20`, ЛКМ — предмет просто падает; гравитация, сопротивление,
  скорость не выше 80;
- путь каждого шага проверяется по сетке клеток (`FlightGridSweep`): преграда — стена на ребре, пустота
  (`ConstBin == 16`), край карты, закрытая дверь; пол (y = 0) и потолок (y = 10) — плоскости (`FlightPlaneSweep`);
- удар — отскок (`FlightReflect`), удар о пол — посадка;
- старт у стены (`ResolveFlightStart`): центр предмета не может оказаться за стеной от камеры; если коробка
  предмета попала в стену, берётся ближайшее свободное место, иначе коробка временно уменьшается и потом
  растёт обратно;
- окно разбивается, незапертая дверь, в которую предмет проходит, открывается, запертая работает как стена;
  `BoxCast` оставлен только для мебели и прочих свободных коллайдеров;
- посадка: `SettleThrown` (как в §11.2); таймаут 8 с остался как страховка.

Удалены `SweepAirborneProps`, `PassesThroughDoorOrWindow`, `ApplyWallBounce`, `TryGetGroundContact`,
`UpdateDoorForThrownProp` и константы `ThrowSweep*` / `ThrowBounce*`.

### 12.2 Стены под дверью: что возвращается, а что нет

**Правило.** Дверь, поставленная на стену, снимает её с **обеих** граней. Когда дверь уходит с этого ребра,
возвращаются **те же** стены. Где дверь стояла с самого начала (ванильный проём) или где стены на момент её
прихода не было, стена **не добавляется**.

| Ребро, которое дверь покидает | Результат |
|---|---|
| дверь сняла здесь стену (одну грань или обе) | эти грани возвращаются (`CloseCell`) |
| стены не было (ванильный проём, открытое ребро) | остаётся открытым |
| ванильное окно (ещё ни разу не переносилось) | закрывается стеной, как и раньше |
| та же дверь на том же ребре, но с другой стороны | ничего не меняется |

**Как устроено** (`CommitDoorMove`, `g2.cs`). Статический словарь `RemovedWalls` (ключ — ребро, `EdgeKey`, один
для обеих сторон) помнит, на каких гранях стояла стена до прихода двери. Словарь меняется только после успешного
переноса; при ошибке откат возвращает биты из снимков. Записи другого или уничтоженного уровня выбрасывает
`PurgeRemovedWalls`. Грань возвращается только на клетке, которая ещё существует. Константа `SealOldDoorway`
заменена этим правилом. Миникарта обновляется как в §11.1.

### 12.3 Проверка в игре

**Броски (ПКМ):** в стену вплотную, с 3 м, под углом, в угол, вдоль стены; вверх (потолок); вниз под ноги и
вперёд-вниз; к краю карты; в закрытое окно (разбивается), в незапертую дверь (открывается), в запертую (отскок);
большой предмет (шкаф, парта) почти вплотную к стене. Предмет не должен проходить сквозь стены и пол. Выпуск ЛКМ
вплотную к стене: предмет падает рядом.

**Двери:**

1. Ванильную дверь перенести на стену: на новом месте стены нет, на старом (проём) стены тоже нет.
2. Эту же дверь перенести дальше: на предыдущей стене стена вернулась на обеих гранях.
3. Вернуть дверь в исходный проём: стена вернулась, а в исходном проёме стены нет.
4. Ванильное окно перенести: на старом месте стена; перенести ещё раз: стена на предыдущем месте вернулась.
5. После каждого шага: одна пара маркеров двери на миникарте, дверь стоит на показанном превью.

### 12.4 Лог (`BepInEx/LogOutput.log`, префикс `[Rebuild the School]`)

| Строка | Значение |
|---|---|
| `Prop thrown; it flies on a swept path…` / `Prop dropped; …` | полёт начат (ПКМ / ЛКМ) |
| `Released next to a wall: …` | старт был вплотную к стене: предмет подтянут и/или коробка уменьшена |
| `Thrown prop hit <стена, закрытая дверь, потолок, коллайдер> at X u/s; bounced.` | первый удар за полёт (для выпуска `Dropped prop hit …`) |
| `Prop '<имя>' thrown came to rest in <комната>; …; wall impacts on the way: N.` | посадка |
| `Settling a landed prop failed…` / `Thrown-prop flight step failed…` / `A prop was still airborne after 8 s…` | ошибка или страховка: предмет вернулся на исходное место |
| `Door move (<Тип>): …; old edge: <что с ним стало>; wall removed at the new edge: True\|False; …` | перенос двери; `old edge`: `wall rebuilt on both faces`, `wall rebuilt on one face`, `walled up (window)`, `left open (it was a doorway)`, `same edge, the door only turned around` |

### 12.5 Ограничения и риски

- Ничего из §12 не запускалось в игре: первый запуск может показать ошибки.
- Высота потолка принята 10 (как в `HighWallsGenerator` и `Entity`), толщина стены ±0,1.
- Пока коробка предмета уменьшена (старт у стены), крупный предмет может визуально чуть заходить в стену;
  центр и коробка столкновений — нет.
- Полёт кинематический: предмет не толкает динамические тела; игрок и `Entity` не преграда для полёта
  (персонажей брошенный предмет толкает, см. §13).
- Невидимые твёрдые коллайдеры, не принадлежащие `Tile`/`Door`/`Entity`, видит только `BoxCast`.
- Реестр дверей обновляется раз в 0,25 с; только что поставленную дверь раньше замечает `BoxCast`.
- Возвращённая стена не проверяет проходимость: она может отрезать комнату. Убрать её можно инструментом стен.
- Память о стенах живёт только в процессе и не сохраняется. Дверь, перенесённая не через `g2`, записи не имеет:
  её старый проём считается открытым.

## 13. Брошенный предмет толкает персонажа со звуком Bang (`g`)

Код этого раздела **не собирался и не запускался в игре**; имена членов игры сверены только по декомпилу BB+.

### 13.1 Что делает

- Только бросок ПКМ; выпуск ЛКМ персонажей не трогает.
- Каждый шаг полёта (`StepFlight`) отрезок, который прошёл центр предмета (с запасом на размер его коробки),
  проверяется на пересечение с границами коллайдеров персонажей из `EnvironmentController.Npcs` (`HitNpcs`).
  Подходят активные, видимые, не замороженные и не раздавленные персонажи (замороженный `Entity` силы не
  применяет). Предмет должен лететь к персонажу, его горизонтальная скорость — не меньше 3.
- **Толчок как у хулигана.** `Bully.Push` делает `entity.AddForce(new Force(направление, pushSpeed, pushAcceleration))`
  со значениями 5 и −5 (сила гаснет за 1 с, сдвиг около 2,5). Здесь тот же вызов; направление — от точки удара
  через персонажа (по горизонтали), скорость = 0,5 · горизонтальная скорость предмета, но от 5 до 25, ускорение
  = −скорость. Бросок на 20 u/s сдвигает персонажа примерно на 5. Числа — константы `NpcPush*` в начале `g.cs`.
- **Звук.** `AudioManager.PlaySingle` на аудио-менеджере самого персонажа, так же 1st Prize играет `audBang`.
  Звук ищется один раз: `SoundObject` с именем `Bang`, иначе `FirstPrize.audBang`; неудачный поиск повторяется
  через 30 с.
- Предмет отскакивает назад (горизонтальная скорость × −0,3). Каждого персонажа он толкает один раз за полёт.
  Стены, двери и пол по-прежнему решает полёт из §12: персонаж за стеной или закрытой дверью не задет.

### 13.2 Проверка в игре

1. Бросить предмет (ПКМ) в персонажа с 5–10 м: персонаж отлетает примерно на 5, слышен Bang, предмет
   отскакивает и падает.
2. Бросить в упор: то же самое.
3. Бросить мимо персонажа: ничего. Бросить в персонажа за закрытой дверью: удар о дверь, персонаж на месте.
4. Выпустить предмет ЛКМ над персонажем: толчка нет.

### 13.3 Лог

| Строка | Значение |
|---|---|
| `Thrown prop hit <имя> at X u/s; pushed it away at Y u/s (Bang).` | толчок выполнен |
| `Bang sound found: <имя>` / `The Bang sound was not found; characters are pushed without it.` | результат поиска звука (при первом попадании) |
| `Pushing a character with a thrown prop failed…` | ошибка; полёт продолжается |

### 13.4 Ограничения и риски

- Имя ассета `Bang` и поле `audBang` взяты из декомпила, в игре не проверялись: нет звука — смотри вторую строку
  лога.
- Граница персонажа — прямоугольник вокруг его коллайдеров; у капсулы по углам он чуть шире.
- Персонаж с `resistAddend` на силы не реагирует (звук прозвучит); замороженный пропускается целиком.
- Персонажи вне `Npcs` не толкаются.
